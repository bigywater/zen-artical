先确认本机到底有没有 ES 服务

文章中的真实数据先回答环境问题，再讨论 API 的语义。

当前工作区没有安装 Python Elasticsearch 客户端，也没有在本机 9200 端口监听的 Elasticsearch 服务。这个事实决定了本文的证据边界：下面可以真实记录依赖和连接探针，但不能伪造索引、分片、评分或集群返回 JSON。

本篇请求形状（服务启动后再执行） GET / GET /_cat/indices?v

真实探针一：客户端是否安装

这个结果来自当前解释器，而不是根据经验推断。

真实实测 
python3 -c "import importlib.util; print(importlib.util.find_spec('elasticsearch') is not None)"
False

输出 False 只说明当前 Python 环境不能直接通过官方客户端发请求。它不说明 Elasticsearch API 本身不存在，也不说明另一台机器的依赖状态。

真实探针二：9200 是否有服务监听

使用 TCP 连接探针，避免把 HTTP 错误页误当成 ES 响应。

真实实测 
python3 -c "import socket; s=socket.socket(); s.settimeout(1); print(s.connect_ex(('127.0.0.1',9200)); s.close())"
connect_ex 1

本机返回 1，对应当前连接失败的结果。因为没有服务端响应，本文不会写任何“实际命中了某个分片”“聚合返回了某个桶”之类的数字。

从请求形状回到 Elasticsearch 执行边界

Elasticsearch 主题至少要分成客户端、HTTP API、协调节点、分片执行和 Lucene 段文件几层。一个请求 JSON 只能描述意图，真正的命中数、分片路由、评分、聚合桶和恢复状态，必须由目标版本的运行实例返回。

这次没有验证的内容

本篇没有验证 Mapping 动态推断、分片分配、聚合结果、BM25 分数、刷新延迟、Translog、快照、安全配置或故障恢复。它们都依赖实际 Elasticsearch 节点和具体版本，当前环境没有满足这个前提。

边界提醒：真实的“未安装”和“端口未监听”也是实验结果；它们不能被包装成 Elasticsearch 集群行为。
