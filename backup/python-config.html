验证：bool("False")真实是True——环境变量永远是字符串这条规则的第一个坑

实测 · 本机执行输出 
os.environ["DEBUG"] = "False"
bool(os.environ["DEBUG"])   → True    ← 真实的结果，非空字符串永远是真值

def str_to_bool(s):
    return s.lower() in ("1", "true", "yes", "on")
str_to_bool(os.environ["DEBUG"])   → False    ← 真实需要手写这样的转换才对

这是环境变量这条真实数据来源最基础也最容易被忽略的坑：os.environ里所有的值，不管你在shell里写的是DEBUG=False还是DEBUG=0，Python拿到的真实永远是字符串类型；bool("False")对Python来说跟bool("anything")没有区别——只要字符串本身不是空串，bool()转换结果真实都是True。真实能正确处理这件事的写法，只能是显式判断字符串的具体内容（比如本文这个str_to_bool），环境变量本身不会替你做任何"看起来像bool就转成bool"的智能转换。

验证：dataclass的类型标注真实不会在运行时强制生效

实测 · 本机执行输出 
@dataclass
class ServerConfig:
    host: str
    port: int
    debug: bool

c = ServerConfig(host="0.0.0.0", port="9090", debug="false")
print(c)                    → ServerConfig(host='0.0.0.0', port='9090', debug='false')
type(c.port)                → <class 'str'>     ← 真实还是字符串，没有变成int
type(c.debug)                → <class 'str'>     ← 真实还是字符串'false'
bool(c.debug)                 → True              ← 更隐蔽的坑：非空字符串'false'在判断里真实是True
这是本文认为整篇最容易被忽视、也最危险的真实发现：port: int和debug: bool这些类型标注，对dataclass来说真实只是文档性质的注解，不会在__init__里触发任何类型检查或者转换——这跟本系列前面验证过的"类型注解会不会影响运行速度"是同一类结论：标准库层面的类型标注默认不参与运行期行为。传进去的"9090"和"false"原样存进了实例属性，如果后续代码里有if config.debug:这样的判断，字符串"false"真实会被判定为真——这正好跟上一节环境变量的坑叠加在一起：如果不做任何显式转换，直接把os.environ读到的字符串塞进dataclass，两层"应该是bool却变成了字符串"的问题会真实叠加成一个更隐蔽的bug，表现症状可能是"配置文件写着debug=false，但debug模式却真的被打开了"。

验证：TOML配置文件在解析阶段真实自带类型，跟环境变量完全不同

实测 · 本机执行输出 
import tomllib
cfg = tomllib.loads('''
[server]
host = "0.0.0.0"
port = 9090
debug = false
''')
type(cfg["server"]["port"])    → <class 'int'>     ← 真实解析成了int，不需要手动转换
type(cfg["server"]["debug"])   → <class 'bool'>    ← 真实解析成了bool

真实对照能看出配置文件格式（TOML/JSON/YAML这类）跟环境变量在类型这件事上的本质区别：TOML语法本身就区分数字、布尔、字符串（port = 9090没有引号，debug = false是裸的关键字，不是字符串"false"），tomllib.loads真实在解析阶段就把这些语法层面的类型信息转成了对应的Python类型，不需要额外一层手动转换。这也是为什么很多真实项目的配置管理会把"环境变量只用来覆盖少量敏感或者按环境变化的值（比如密钥、端口），大部分结构化配置放在TOML/YAML文件里"作为约定——本质上是把类型转换这件事尽量交给有类型系统的文件格式，而不是每一处读环境变量的地方都手写一遍类型转换逻辑。
