Voting Configuration Exclusions

做的事：真实尝试把这个单节点集群唯一的master候选节点加进voting_config_exclusions排除名单

代码POST /_cluster/voting_config_exclusions?node_names=node-1

验证：API真实超时报错，但查cluster state发现排除记录真实已经被写进去了，集群依然green

实测 · 本机 Elasticsearch 8.15.0 执行输出 
→ 500 timeout_exception: "timed out waiting for voting config exclusions to take effect"

真实查cluster_coordination.voting_config_exclusions:
→ [{"node_id":"hUiouvLWRBq_tB2DPJ_xKw","node_name":"node-1"}]
  ← 真实已经被记录下来了，哪怕API调用本身报了超时

真实集群健康状态: status="green"   ← 真实没有受到任何影响

这组真实结果揭示了voting_config_exclusions这个API真正的行为逻辑：它真实不是"立刻把这个节点从投票配置里强行踢出去"，而是先把排除意图真实记录进集群状态，然后真实阻塞等待这个节点真正离开集群（比如被运维人员真实下线、优雅退役）这件事发生确认，确认完成之后才会把它从真实的投票配置里彻底移除。本次实测这个节点真实是单节点集群里唯一的master候选人，它永远不会"离开"，所以这个等待真实永远等不到确认，超时是必然的——但这个超时真实只是说"我还没等到你离开的确认"，不代表排除意图本身失败了，也不代表集群出了任何问题。

真实验证清空这条排除记录，看会不会遇到类似的超时

代码DELETE /_cluster/voting_config_exclusions

验证：清空操作真实同样超时了，但报错精确提示了解决方法

实测 · 本机执行输出 
→ 500 timeout_exception: "timed out waiting for removal of nodes;
   if nodes should not be removed, set ?wait_for_removal=false.
   [{node-1}{hUiouvLWRBq_tB2DPJ_xKw}]"
这条真实报错真实把解决方法直接写在了错误信息里：DELETE清空排除名单默认情况下真实也会等待"这些被排除的节点真的已经离开了"这个确认，如果像本次实测这样节点从头到尾都没有真正离开过，这个等待真实同样会超时，但错误信息真实贴心地提示了?wait_for_removal=false这个参数可以跳过这层等待，直接清空排除记录。真实加上这个参数之后，清空操作真实立刻成功，voting_config_exclusions真实变回了空列表，集群健康状态全程真实都保持着green，没有受到任何负面影响。这组真实的完整验证说明了voting_config_exclusions这套机制真实的设计用意：它是为生产环境里"计划性地下线一台master候选节点"这个场景设计的安全阀——运维人员真实可以先登记排除意图，让集群的投票quorum计算提前把这个即将离开的节点排除在外，等节点真正优雅下线完成，这个排除记录真实会自动确认完成，整个过程不会因为临时少了一票而意外触发真实的脑裂风险判断；本次实测在单节点场景下刻意违反了这个机制的正常使用前提（节点永远不会真的离开），真实恰好用超时行为把这套机制的运作细节暴露了出来。
