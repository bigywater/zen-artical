三色标记与写屏障:并发标记期间新指针怎么不丢对象

并发 GC 要解决一个核心问题:程序在标记期间还在改指针,怎么保证活的对象不被漏标?答案是写屏障。这篇用 gctrace 看一次 GC 的真实形态,读运行时源码里的设计描述,在汇编里找到屏障,量出屏障的代价,并对比 Go 1.27.1 默认的新 GC 实现。

标记阶段里一次指针写的耗时(GC 空闲时是 2.37 ns);整数写不受影响

gctrace 的每行是一次 GC:两个 STW(清扫终止、标记终止)都只有几十微秒,中间的并发标记占大部分墙钟时间,但那段时间里程序在继续运行。3->4->1 MB 是 GC 开始时的堆、标记结束时的堆、存活的堆。源码开头也说明了总体设计:并发、标记清扫、非分代、非压缩。

为什么需要写屏障

实测 · 本机执行输出 
  mgc.go:8-12
    // GC threads to run in parallel. It is a concurrent mark and sweep that uses a write barrier. It is
    // non-generational and non-compacting. Allocation is done using size segregated per P allocation
    // areas to minimize fragmentation while eliminating locks in the common case.
    //
    // The algorithm decomposes into several steps.
  mgc.go:25-27
    //
    //    a. Stop the world. This causes all Ps to reach a GC safe-point.
    //
  mgc.go:36-46
    //    scanned until all Ps have enabled the write barrier, which is
    //    accomplished using STW.
    //
    //    b. Start the world. From this point, GC work is done by mark
    //    workers started by the scheduler and by assists performed as
    //    part of allocation. The write barrier shades both the
    //    overwritten pointer and the new pointer value for any pointer
    //    writes (see mbarrier.go for details). Newly allocated objects
    //    are immediately marked black.
    //
    //    c. GC performs root marking jobs. This includes scanning all
  mbarrier.go:24-34
    // Go uses a hybrid barrier that combines a Yuasa-style deletion
    // barrier—which shades the object whose reference is being
    // overwritten—with Dijkstra insertion barrier—which shades the object
    // whose reference is being written. The insertion part of the barrier
    // is necessary while the calling goroutine's stack is grey. In
    // pseudocode, the barrier is:
    //
    //     writePointer(slot, ptr):
    //         shade(*slot)
    //         if current stack is grey:
    //             shade(ptr)

三色标记里,标记完成的对象是黑色,待扫描的灰色,未访问的白色;白色最后被回收。如果程序在标记期间把一个白色对象的唯一引用写进一个已经变黑的对象、同时又删掉了原来的引用,这个对象就会被漏掉。写屏障拦截每一次指针写入,保证这种情况不会发生。源码里的描述是:混合屏障,既 shade 被覆盖的旧指针,也(在当前栈是灰色时)shade 新写入的指针;并且标记期间新分配的对象直接标黑。

屏障的代价只在标记时

实测 · 本机执行输出 
  GC 空闲(没有后台 GC)                     指针写 a.next = b 中位 2.37 ns/次;整数写 a.val[0] = i 中位 1.01 ns/次
  后台不停地 runtime.GC()                 指针写 a.next = b 中位 17.59 ns/次;整数写 a.val[0] = i 中位 1.11 ns/次;这段时间后台 runtime.GC() 完成了 143 轮

实测指针写在 GC 空闲时 2.37 ns,标记阶段升到 17.59 ns(约 7.4 倍);整数写不受影响。这个实验里后台连续不停地 GC,标记阶段占了几乎所有时间,是最坏情形;实际程序里标记阶段只占一部分时间。
