JDBC 连接池:复用连接也要重置状态

连接池让连接「复用」,也让连接上的状态跟着复用。这篇用真实的 HikariCP 看归还时重置了什么、没重置什么,耗尽与泄漏的表现,以及服务端杀掉连接之后连接池要多久才发现。

SET / schema / 锁
HikariCP 归还连接时不会重置:会话变量(SET)、PG 的 schema、MySQL 的 catalog、临时表、advisory lock / get_lock
300 ms vs 800 ms
连接被服务端杀掉后再借:500 ms 内(aliveBypassWindowMs)拿到坏连接,之后会验证并重建
1647 → 31 µs
每次新建物理连接与从池里借出 + 归还 + select 1 的耗时(PG,本机)

归还时重置了什么

实测 · 本机执行输出 
  ── PostgreSQL
  新借出的连接状态:autoCommit=true readOnly=false isolation=2 catalog=lab schema=public;物理连接 id 46596
  第一个使用者改成:autoCommit=false readOnly=true isolation=8 catalog=lab schema=public
  还回去再借(同一物理连接 true):autoCommit=true readOnly=false isolation=2 catalog=lab schema=public(Hikari 归还时重置了 autoCommit / readOnly / isolation)
  改 catalog 后归还,再借:(PG 不能切换 catalog)
      当前 catalog = lab
  setSchema(pg_catalog) 后归还,再借:getSchema = pg_catalog;current_schema = pg_catalog
  会话变量(SET)归还后再借:application_name = leaked_name;statement_timeout = 3s;search_path = pg_catalog(没有被重置,泄漏给下一个使用者)
  临时表归还后再借:1(临时表还在)
  advisory lock 归还后再借:pg_locks 里本会话持有的 advisory lock 数 = 1(锁跟着物理连接走,没有释放)
  未提交的 insert 之后 close() 归还,再借查 acct:0 行(Hikari 在归还时 rollback)
  ── MySQL
  新借出的连接状态:autoCommit=true readOnly=false isolation=4 catalog=lab schema=null;物理连接 id 10
  第一个使用者改成:autoCommit=false readOnly=true isolation=8 catalog=lab schema=null
  还回去再借(同一物理连接 true):autoCommit=true readOnly=false isolation=4 catalog=lab schema=null(Hikari 归还时重置了 autoCommit / readOnly / isolation)
  改 catalog 后归还,再借:
      当前 catalog = mysql(MySQL 上 Hikari 没有把 catalog 恢复成 lab;下一个使用者拿到的是被改过的 catalog)
  会话变量(SET)归还后再借:@leak = 42;wait_timeout = 77;sql_mode = “”(没有被重置,泄漏给下一个使用者)
  临时表归还后再借:1(临时表还在)
  get_lock 归还后再借:is_used_lock('lk') = 连接 10,当前连接 10(锁仍被持有)
  未提交的 insert 之后 close() 归还,再借查 acct:0 行(Hikari 在归还时 rollback)
