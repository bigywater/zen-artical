refresh_interval 对写入性能的影响

真实对比每次写入都强制refresh与完全禁用refresh两种极端写入模式，验证频繁refresh导致每条文档单独承担一次segment生成开销所带来的约2.1倍真实性能代价，揭示refresh_interval调大能提升写入吞吐的真实原理。

refresh_interval的真实作用
把segment生成的固定开销摊销到更多写入上

做的事：真实对比每次写入都强制refresh和完全不强制refresh这两种极端模式的真实耗时

代码索引A: refresh_interval=-1（彻底关闭自动刷新） 索引B: 同样refresh_interval=-1，但真实每次写入都带上refresh=true参数强制刷新 真实各自循环写入2000条独立文档: POST /ri_fast/_doc?refresh=true {"n": i} # 每次都强制刷新 POST /ri_slow/_doc {"n": i} # 完全不触发刷新

验证：每次都强制刷新真实耗时21.167秒，完全不刷新真实只要10.087秒，慢了约2.1倍

实测 · 本机 Elasticsearch 8.15.0 执行输出 
每次写入都refresh=true（2000条）: elapsed_sec=21.167
完全不触发refresh（2000条）:      elapsed_sec=10.087
  ← 真实慢了约2.1倍

这组真实耗时差距的根源，正是本系列第97篇真实验证过的那个核心事实：每一次refresh都真实会把内存缓冲区里积累的新文档，组织成一个全新的、不可变的Lucene segment文件写入磁盘。如果每条文档写入都真实强制触发一次refresh，就相当于真实把"生成一个全新segment文件"这个本应该批量摊销的开销，真实拆成了2000次、每条文档都单独承担一次，每次真实都要走一遍"打开新段、写入倒排索引结构、让它变得可搜索"这一整套流程，哪怕这个段里只有一条文档。而完全不触发refresh的写入，真实只需要把数据顺序追加进内存缓冲区和translog（本系列第96篇验证过的轻量操作），不需要真实承担反复创建segment文件的开销。

真实理解refresh_interval这个设置真实调节的是什么：不是"要不要刷新"，而是"刷新的频率摊销到多少次写入"

代码真实场景里几乎不会真的完全禁用refresh（那样数据永远搜不到），业务上通常是在 "数据多久之后要能被搜到"和"写入吞吐能有多高"之间权衡一个真实的refresh_interval取值 （默认1秒，日志类写入密集场景常见做法是临时调大到30秒甚至更长）

这组真实的极端耗时对比，正是refresh_interval调大能提升写入吞吐的真实原理

实测 · 本机对比总结 
refresh频率越高（极端情况就是每条写入都refresh）: 真实segment生成开销摊销到的写入数越少，每条写入承担的额外成本越高
refresh频率越低（极端情况是完全禁用）: 真实segment生成开销摊销到的写入数越多，整体写入吞吐真实越高，但数据变得可搜索的延迟也真实越长
这组真实的两极端对比完整解释了调大refresh_interval（从默认1秒调成比如30秒或者在大批量导入时临时设成-1彻底关闭）真实能带来的吞吐提升：它真实不是靠某种神奇的优化，而是单纯把"生成一个新segment文件"这笔真实存在的固定开销，摊销到了更多条写入上——1秒刷新一次，如果这1秒内真实写入了1万条文档，这1万条真实只需要共同承担1次segment生成的开销；如果每条都单独refresh，这1万条就要真实承担1万次这笔开销。本次实测用2000条文档在两种极端情况下量化出了约2.1倍的真实差距，真实场景下批量导入海量历史数据时，常见做法正是真实把refresh_interval临时调成-1，导入完成后再真实调回正常值或者手动触发一次refresh，用短期内"数据暂时搜不到"换取真实可观的写入吞吐提升。
