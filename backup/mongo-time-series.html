时序集合:bucket 文档长什么样

时序集合里的数据到底怎么存?这篇用 3 个传感器的测量,通过 rawData 读出底层 bucket 文档的 control、meta、data,再验证 bucket 的拆分上限、磁盘占用和 update / delete 的限制。

1200 → 3
3 个传感器各 400 个测量,底层只有 3 个 bucket 文档
1000
单个 bucket 最多的测量数,3000 个测量拆成 3 个 bucket
2%
周期性合成数据下时序集合占盘是普通集合的比例(真实数据会高得多)
← 上一篇 TTL 索引:过期文档什么时候才真正被删

占盘

实测 · 本机执行输出 
  时序集合: storageSize 24,576,bucket 数 60,平均每个 bucket 714
  普通集合: storageSize 1,318,912,文档数 60,000
  比例: 时序集合是普通集合的 2%

列存加压缩让时序集合远小于普通集合;本文数据是周期性合成的,压缩得格外好,不能当作真实数据的比例。

查询与限制

实测 · 本机执行输出

  test> db.m.updateMany({sensor: "A"}, {$set: {sensor: "A2"}})
  {
    acknowledged: true,
    insertedId: null,
    matchedCount: 400,

  test> db.m.deleteOne({temp: 20})
  { acknowledged: true, deletedCount: 1 }
  test> db.m.deleteMany({sensor: "B"})
  { acknowledged: true, deletedCount: 400 }

查询先扫 bucket 再用 $_internalUnpackBucket 展开;自动建 meta + 时间的索引;非 multi 的 update 不允许,按 meta 的 updateMany / deleteMany 可以。
