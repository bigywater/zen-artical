做的事：真实对比忙等轮询和Event.wait()两种停止信号的写法

代码stop_event = threading.Event() def worker_poll(): # 写法一：忙等 count = 0 while not stop_event.is_set(): count += 1 def worker_wait(): # 写法二：Event.wait(timeout) count = 0 while not stop_event.wait(timeout=0.05): count += 1 th.start(); time.sleep(0.2); stop_event.set(); th.join()

验证：忙等轮询真实空转了800万次，跑满一个CPU核心

实测 · 本机执行输出 
busy poll: stopped after 0.222 s, loop iterations: 8008235

这是while not stop_event.is_set(): count += 1这种写法真实的代价：0.2秒的等待期间，这个线程真实一刻不停地检查is_set()并自增计数器，真实跑了超过800万次循环——这段时间里这个线程真实独占了一个CPU核心，做的全部是空转判断，没有产出任何真正有意义的工作。如果这是一个后台线程，真实会让整个进程的CPU占用率长期居高不下，即使这个线程实际上什么正事都没在做。

验证：Event.wait(timeout)真实几乎不占CPU，响应速度反而更快

实测 · 本机执行输出 
event.wait(timeout=0.05): loop iterations before stop: 2      ← 真实只循环了2次
time from set() to thread actually exiting: 0.0001 s            ← 真实几乎瞬间响应
这组对比揭示了Event.wait(timeout=...)真实的双重优势：一方面，wait()内部真实是基于Condition实现的（跟本系列上一篇验证的threading.Condition是同一套机制），线程在等待期间真实是被操作系统挂起的，不占用CPU，本文这次0.12秒的等待窗口里真实只循环了2次（每次最多等0.05秒就重新检查一次，纯粹是为了防止set()因为某种极端情况错过而设的兜底超时）；另一方面，set()被调用的那一刻，真实会立刻唤醒所有正阻塞在wait()里的线程（正如上一篇验证过的Condition.notify机制），不需要等到下一次超时轮询才发现状态变了，本文测出从set()调用到线程真实退出只花了0.0001秒——比"每次都要判断一下"的忙等反而响应得更快，因为它是真实被主动唤醒的，不是被动轮询发现的。真实的结论很直接：Event这种"阻塞等待+可被立刻唤醒"的设计，同时解决了忙等轮询"浪费CPU"和"响应有延迟（取决于轮询间隔）"这两个问题，timeout参数存在的真实意义只是给等待设一个兜底上限，不是让它退化成定期轮询。
