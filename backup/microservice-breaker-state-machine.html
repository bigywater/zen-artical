熔断器的状态机:三个状态、半开放行多少探测请求,手写版与 gobreaker 对照

  半开要连续 N 个成功才关闭,所以下游成功率 q 不高时,N 越大越容易在半开里又失败一次、重新打开(q^N 是一轮半开通过的概率)

    本文用到的工具与边界

    • 本机 macOS 27 arm64 / Python 3.14.8 / Go / nginx / Envoy / etcd / Consul / Nacos / OpenTelemetry / Prometheus(按各篇注明用到哪些及版本);所有服务都是本机自己起的进程,端口 9150 以上,只监听 127.0.0.1,不连任何外部服务,不碰本机已有的实例;故障用 kill -9 进程、让连接断开或在代码里注入延迟与错误来制造;计时用 time.perf_counter,数字每次运行会有小幅抖动。手写的 Breaker 是 Python 3.14 的我自己的实现(连续失败计数、半开最多放行 N 个、N 个连续成功才关闭);gobreaker 是 github.com/sony/gobreaker/v2 v2.4.0,用 Go 1.27.1 编译,Settings 里 MaxRequests 3、Interval 0、Timeout 1025 ms;两边的剧本是每 50 ms 调用一次的函数,不经过网络;第三节用的是真实的本机 HTTP 服务和 20 个并发线程;第四节用虚拟时钟(不真的 sleep)
    • 没有验证:按失败率或慢调用率的统计窗口触发(见下一篇);gobreaker 的滚动窗口(BucketPeriod)与 Interval 的行为;真实网络和多实例下各实例熔断器状态不共享的影响;第三节只跑了一轮,三个放行数的“到达下游的请求”差异在噪声内,只有半开期间的失败数(2、6、18)的规律是由放行数直接决定的
