Zone Awareness 跨可用区副本

真实独立搭建一个2节点zoneA+1节点zoneB的3节点Elasticsearch集群，验证不开awareness时主副本有真实概率被同时分到同一个可用区，开启非强制awareness.attributes=zone后连续测试全部实现跨区分布，并真实kill掉唯一的zoneB节点模拟整个可用区下线，验证集群仅降级为yellow、全部主分片健在且能正常读写，证明zone awareness真实换来的是可用区级故障下的数据存活保障。

这组真实数据直接暴露了不开zone awareness时的真实风险：ES默认的分配均衡器真实只关心"每个节点上的分片数量是否均衡"，完全不关心"这些节点分别属于哪个可用区"。本次实测6个索引里，真实有2个（zt_noaware1和zt_noaware4）的主分片和副本被同时放进了zoneA这一个区（分别落在zone-node-1和zone-node-3两台不同的机器上，满足了same_shard决策器"不能放同一个节点"的要求，但两台机器真实都在同一个可用区），一旦zoneA真实整体下线，这2个索引真实会彻底丢失所有数据，不只是丢失冗余。

真实开启非强制的awareness.attributes=zone，重复同样的6次测试

代码PUT /_cluster/settings {"persistent":{ "cluster.routing.allocation.awareness.attributes":"zone" }} 真实删除刚才的6个索引，重新连续PUT 6个索引 zt_aware1..6，均1主1副

验证：这次真实6个索引无一例外全部被分到了不同的zone，零同区情况

实测 · 本机执行输出 
zt_aware1 : zone-node-1(zoneA) + zone-node-2(zoneB)  → 跨区 ✓
zt_aware2 : zone-node-2(zoneB) + zone-node-3(zoneA)  → 跨区 ✓
zt_aware3 : zone-node-1(zoneA) + zone-node-2(zoneB)  → 跨区 ✓
zt_aware4 : zone-node-2(zoneB) + zone-node-3(zoneA)  → 跨区 ✓
zt_aware5 : zone-node-1(zoneA) + zone-node-2(zoneB)  → 跨区 ✓
zt_aware6 : zone-node-2(zoneB) + zone-node-3(zoneA)  → 跨区 ✓
对比前后两组真实数据能看出一个重要的真相：本系列上一篇验证过非强制awareness.attributes在"只有1个可选节点"的场景下不会产生任何额外的硬性拒绝（deciders列表里不会多出任何东西），但这不代表它没用——本次实测场景里有3个真实候选节点可选，非强制awareness真实在ES内部的打分排序阶段发挥了作用，持续、稳定地把"是否跨区"作为优先考虑的因素去排列候选节点的优先级，哪怉它从不会像forced awareness那样直接否决一个分配方案，只要有合理的跨区选项存在，它真实几乎总能让ES选中那个选项。这两篇放在一起才是完整的真相：非强制awareness真实不是"没用"，而是"软性但在多节点场景下真实有效"的平衡策略。
