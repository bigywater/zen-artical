场景二:Redis 里的任务体与页面缓存,小对象怎么压

爬虫的任务队列和页面缓存都放在 Redis 里,内存是钱。任务体该用什么格式,压不压缩,打包多大,缓存的页面要不要压缩?这篇在本机独立的 Redis 上逐项量内存、吞吐和网络流量。

队列里一个任务占的 Redis 内存:JSON 与 JSON + zstd-3 + 字典
68.7 对 14.9 MiB
缓存 5000 个页面:原样存放与 zstd-3 + 字典
265.8 对 36.1 字节
一个任务占的内存:每元素 1 个任务与每元素 50 个任务(整体 zstd-3)

任务体

实测 · 本机执行输出 
  任务数 100000;紧凑 JSON 平均 376 字节

任务里很多内容是每个任务都相同的(UA、语言、referrer)。直接把常量字段拿出任务体,JSON 就从 392.9 降到 183.1 字节/任务;换 Protobuf 是 265.8;JSON 加 zstd 字典是 52.8。字典能把这些重复统统吃掉。

MessagePack 和 Protobuf 的编码解码比 JSON 快;压缩加字典的 JSON 入队 128789 个/秒,和纯 JSON(138308)接近。在 Python 里瓶颈是编码解码和 Redis 往返,不是压缩本身。

把 N 个任务打包成一个元素再压缩,每任务内存随 N 增大迅速下降(1 个 265.8,10 个 63.4,50 个 36.1,200 个 31.0 字节)。但租约、重试、去重都以元素为粒度,崩溃时要重做整包(见第 66 篇)。

缓存页面

实测 · 本机执行输出 
      每元素任务数     元素数   Redis 内存增量     每任务内存
           1  100000       25.4MiB    265.8B
          10   10000        6.0MiB     63.4B
          50    2000        3.4MiB     36.1B
         200     500        3.0MiB     31.0B
  (元素里装的任务越多,每个任务的内存越小,但一个 worker 取走一个元素就是取走 N 个任务,崩溃时要重新入队 N 个;租约、重试、去重都以元素为粒度)

13 KiB 的页面原样存 68.7 MiB(5000 页),lz4 29.6 MiB,zstd-3 20.5 MiB,zstd-3 加字典 14.9 MiB;读取加解压的吞吐 lz4 最快,zstd 约 46000/秒,brotli q5 只有 24219/秒。缓存适合 zstd-3 或加字典,生成一次读很多次。

同样 300 字节,列表元素额外占 16.9 字节,单独的 key 67.3,哈希 field 71.3。把小对象放进列表比单独的 key 省内存。

什么时候别压

实测 · 本机执行输出 
  列表元素 RPUSH q           每个元素共占  316.9 字节(载荷 300 字节,额外  16.9 字节)
  单独的 key SET k:i        每个元素共占  367.3 字节(载荷 300 字节,额外  67.3 字节)
  哈希 field HSET h        每个元素共占  371.3 字节(载荷 300 字节,额外  71.3 字节)
  集合成员 SADD s            每个元素共占  341.1 字节(载荷 300 字节,额外  41.1 字节)

任务体已经很小(比如只有 url),压缩的收益有限,而每个任务加字典后要保证 worker 和队列里的字典 ID 一致,版本升级时队列里还有旧字典压的任务,要继续能解(见第 17 篇)。
