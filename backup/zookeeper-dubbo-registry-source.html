注册的代码很短:

org/apache/dubbo/registry/zookeeper/ZookeeperRegistry.java(dubbo-registry-zookeeper 3.3.6) public void doRegister(URL url) { try { checkDestroyed(); zkClient.create(toUrlPath(url), url.getParameter(DYNAMIC_KEY, true), true); ... } private String toUrlPath(URL url) { return toCategoryPath(url) + PATH_SEPARATOR + URL.encode(url.toFullString()); }

URL.encode 把完整服务 URL 编码成节点名,所以节点名里没有 / 号(见注册中心数据模型)。create(path, dynamic, true) 里的第二个参数是 dynamic(默认 true),决定是临时节点;我没有测 dynamic=false(应该是持久节点,只读了代码)。

杀进程 vs session

同一模块 util/CuratorFrameworkUtils.java protected static int DEFAULT_SESSION_TIMEOUT_MS = 60 * 1000; ... int sessionTimeoutMs = connectionURL.getParameter(SESSION_KEY, DEFAULT_SESSION_TIMEOUT_MS);
实测 · 本机执行输出 
  kill -9 后 /dubbo/Greeter/providers 下的 P1 节点在 16.1 s 后消失(Dubbo 默认注册中心 session 60 s,服务端 maxSessionTimeout = 20 × tickTime = 20 s)
  这期间消费者共 83 次调用,失败 0 次(错误类型 []) —— 我的推断(没有进一步验证):进程被 kill -9 时操作系统关闭了它的 TCP 连接,Dubbo 消费者据此不再向它发请求,没有等 ZooKeeper 的通知
  节点移除之后的 5 秒内失败次数: 0

这里 Dubbo 默认请求 60 s,服务端按 会话超时的协商规则截断。实测 cons 里这两个会话的 to=20000(session=3000 时是 3000)。

冻结与正常退出

实测 · 本机执行输出 
  冻结后 P1 的节点在 2.9 s 后消失;期间消费者调用 16 次,失败 1 次(错误类型 ['ERR RpcException'])
  最后一次失败在冻结后 0.3 s;节点消失之后 3 秒内失败 0 次
实测 · 本机执行输出 
  SIGTERM 后 P2 的节点 0.02 s 消失;SIGTERM 后 4 秒内消费者调用 10 次,失败 0 次

三种「下线」方式对消费者的影响:正常退出(先注销)几乎无感;进程被杀(TCP 断开)时我观察到没有失败(推断是 Dubbo 自己发现了连接断开);进程冻结或网络断开(TCP 没断)才真正依赖 ZooKeeper 的会话过期。对照服务发现那篇自己写的消费者(没有这层保护,kill -9 时有请求失败)。
