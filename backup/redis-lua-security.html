Redis Lua 安全边界

Redis 允许客户端提交一段 Lua 脚本在服务端运行。那它能碰到什么?能不能读文件、执行系统命令、改全局环境?ACL 对脚本内部有没有效?这篇只做一件事:在本机的 8.10.2 上把沙箱的边界逐条试出来,并给出限制脚本时容易漏掉的地方。

os 只有 clock
脚本里没有 io / package / require / dofile / print,os 只剩 clock
逐条检查
ACL 对脚本里的每一次 redis.call 都生效;+eval 不等于什么都能做
漏一半
只禁 eval / evalsha / eval_ro / evalsha_ro 四条时,SCRIPT LOAD / FUNCTION LOAD / FCALL 仍被允许;用 -@scripting 才是全拒

全局环境只读

实测 · 本机执行输出 
  x = 1(创建全局变量)                → ERR Attempt to modify a readonly table
  _G.y = 1                     → ERR Attempt to modify a readonly table
  string.foo = 1(改标准库表)        → ERR Attempt to modify a readonly table
  redis.foo = 1(改 redis 表)     → ERR Attempt to modify a readonly table
  local z = 1(局部变量)            → 1
  setmetatable(_G, {})         → ERR Attempt to modify a readonly table
  os = nil                     → ERR Attempt to modify a readonly table

创建全局变量、改标准库表、改 redis 表、给 _G 设元表,全部报 Attempt to modify a readonly table。脚本之间不能通过全局变量互相传东西——要传就走 Redis 里的 key。

CONFIG、ACL、SUBSCRIBE、MONITOR、WATCH、MULTI、EVAL、SAVE、DEBUG、SCRIPT、CLIENT、SLAVEOF 被拒;SET、KEYS、FLUSHDB、BLPOP 可以。这是「不许改服务器状态、不许阻塞连接」的一条线,不是「不许破坏数据」的线——所以能执行 EVAL 的人,能做的数据破坏跟他自己直接执行命令一样多,取决于他的 ACL。(没有测 SHUTDOWN 等其余命令。)

ACL 在脚本内部

实测 · 本机执行输出 
  luser 的脚本 GET app:1                        → None
  luser 的脚本 GET other:1                      → ERR ACL failure in script: No permissions to access a key
  luser 的脚本 DEL app:1                        → ERR ACL failure in script: User luser has no permissions to run the 'del' command
  luser 的脚本 KEYS *                           → ERR ACL failure in script: User luser has no permissions to run the 'keys' command
  luser 的脚本 SET app:2(KEYS 里没声明该 key)        → OK
  luser 的脚本 pcall(DEL app:1)                 → ERR: ERR ACL failure in script: User luser has no permissions to run the 'del' command
  EVAL_RO 里 SET → ERR Write commands are not allowed from read-only scripts.

脚本里每次 redis.call 都按调用者的 ACL 检查(命令和 key 都查)。redis.pcall 把 ACL 失败作为错误值返回而不是终止脚本。没在 KEYS 里声明的 key,只要符合 ACL 的 key 模式仍然可以访问(单机下的实测)。EVAL_RO 里写命令被拒。

脚本相关的命令有 21 条(见上面 @scripting 的完整列表)。只禁 eval 系列四条,FUNCTION LOAD 后 FCALL 仍然能跑 Lua。要禁就用 -@scripting,然后 ACL DRYRUN 验一遍。

死循环与 SCRIPT KILL

实测 · 本机执行输出 
  busy-reply-threshold 默认值: 5000 ms
  纯死循环:另一个连接的 PING 等了 390 ms 才得到 → BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.
  SCRIPT KILL → OK;死循环那条连接得到 → ERR Script killed by user with SCRIPT KILL...
  先 SET 再死循环:PING → BUSY Redis is busy running a script. You can only call SCRIPT KILL or SHUTDOWN NOSAVE.
  SCRIPT KILL → UNKILLABLE Sorry the script already executed write commands against the dataset. You can either wait the script termination or kill the server in a ha
  SHUTDOWN NOSAVE → 连接断开(进程退出) EOFError
  进程还在运行吗: False

脚本运行时服务器是单线程忙碌的,其它连接的命令要等。超过 busy-reply-threshold(默认 5000 ms;别名 lua-time-limit)后,其它连接得到 BUSY,只能 SCRIPT KILL 或 SHUTDOWN NOSAVE。脚本一旦写过数据,SCRIPT KILL 返回 UNKILLABLE,只剩 SHUTDOWN NOSAVE。所以没有写权限的用户跑死循环,伤害是可恢复的;有写权限的,只能停服务。
