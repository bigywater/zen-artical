Consul:agent、server 与 gossip 的分工,健康检查类型与状态流转

Consul 里 server、client agent、gossip 各管什么?一个节点没了多久能发现?HTTP、TTL、TCP 检查的状态怎么流转,failures_before_critical 有什么用?server 失联时服务注册会怎样?这篇用 3 个 server 加 2 个 client agent 逐项量出来。

5.10 ~ 5.37 s
SIGKILL 一个 client agent 后,gossip 判它 failed(服务变 critical)的用时,三次
2.33 ~ 2.96 s
failures_before_critical=3 的 HTTP 检查,从后端返回 500 到变 critical 的用时(默认设置只要 0.44 ~ 1.04 s)
3.39 s
server 恢复后 catalog 里出现 agent 本地早已登记的 api,以及 dep 变 critical 的用时

gossip 与节点故障

实测 · 本机执行输出 
  怎么没的         | 成员状态不再是 alive(s) | serfHealth 变 critical(s) | 服务不再出现在 ?passing(s)  | 结束时                  
  -------------+------------------+--------------------------+----------------------+----------------------
  SIGKILL      | 5.10             | 5.10                     | 5.10                 | catalog 1 / passing 0
  SIGKILL      | 5.35             | 5.35                     | 5.35                 | catalog 1 / passing 0
  SIGKILL      | 5.37             | 5.37                     | 5.37                 | catalog 1 / passing 0
  consul leave | 0.06             | -(节点已被移除,没有 serfHealth)  | 0.25(节点从 catalog 消失) | catalog 0 / passing 0
  SIGKILL 的节点被 gossip 判为 failed 要几秒(探测、怀疑、确认);在那之前服务照样 passing。节点被标成 failed 之后,它上面的服务因为 serfHealth 变成 critical 而不再出现在 ?passing 里,但 catalog 里还在。优雅离开则是节点自己通知集群,节点直接从 catalog 里消失

被杀的节点几秒后才被判为 failed,在那之前服务照样 passing;优雅离开则立刻从 catalog 消失。

HTTP 检查的状态流转

实测 · 本机执行输出 
  刚登记时(后端一直是 200):default critical,slow critical;变成 passing 用了 default 0.29 s,slow 0.17 s(从登记调用返回算起)
  后端状态码改变 | default:到目标状态用的秒数(6 轮范围) | slow(3 次失败 / 2 次成功):同上
  --------+--------------------------+-----------------------
  200→429 | 0.06~0.99                | 0.42~0.95             
  429→500 | 0.44~1.04                | 2.33~2.96             
  500→200 | 0.18~0.87                | 1.08~1.80             
  各情形下 Output 字段的开头(原样):
    500            'HTTP GET http://127.0.0.1:9182/: 500 Internal Server Error Output: x'
    429            'HTTP GET http://127.0.0.1:9182/: 429 Too Many Requests Output: x'
    后端响应超过 timeout 'Get "http://127.0.0.1:9182/": context deadline exceeded (Client.Timeout exceeded while awaiting headers)'
    后端已停(连接被拒)     'Get "http://127.0.0.1:9182/": dial tcp 127.0.0.1:9182: connect: connection refused'

HTTP 检查按 interval 轮询,状态码 429 是 warning;failures_before_critical 和 success_before_passing 决定翻转的速度。

各个入口怎么对待 warning

实测 · 本机执行输出 
  接口                               | 实例数 | 内容                                        
  ---------------------------------+-----+-------------------------------------------
  catalog(/v1/catalog/service/tri) | 3 个 | 不看健康状态                                    
  /v1/health/service/tri           | 3 个 | tri-1:passing tri-2:warning tri-3:critical
  /v1/health/service/tri?passing   | 1 个 | tri-1                                     
  DNS SRV tri.service.consul       | 2 个 | tri-1 tri-2                               
  四个入口对 warning 实例的处理不一样:catalog 全部列出,health 列出并带状态,?passing 去掉 warning,DNS 的 SRV 应答里有 warning 的实例、没有 critical 的实例

catalog 不看健康状态,?passing 去掉 warning,DNS 的应答里有 warning、没有 critical。
