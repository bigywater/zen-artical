TCP 队头阻塞:一个包丢了,后面的数据都在等

TCP 保证按序交付,这个保证有代价:一个包丢了,后面已经到达的数据也只能在接收缓冲区里干等。这篇用 netlab 造丢包,逐条测消息从发出到被应用读到的延迟,看队头阻塞到底拖慢了多少、一次丢包会连累几条消息、拆成多条连接又能缓解多少。

28.8%
TCP 单连接里延迟超过 80 ms 的消息占比(UDP 为 0%,但丢 3%)
972 ms
序号 70 补上的那一刻,后面 20 条消息在同一时刻被一起交给应用
9 条
一次队头阻塞事件拖住的消息数的中位数(最大 34)

对比 UDP 与 TCP

实测 · 本机执行输出 

  
UDP 不重传,延迟全在 50~53 ms,代价是丢 3% 的消息;TCP 一条不丢,但 28.8% 的消息延迟超过 80 ms,p99 229.8 ms。

    TCP 16 条连接轮流发           1500       0       50.3      50.9     311.1      469.8      82(5.5%)
  理论:单程 50 ms;TCP 丢一个包后要等快速重传(约 1~2 个 RTT 以上)或 RTO(lo0 下限 ≈ 230 ms)才能补上,所有排在它后面的消息都被迫等待

  
连接拆得越多,被拖住的消息比例越低(28.8% → 8.7% → 5.5%),16 条连接的尾部延迟却更高。
