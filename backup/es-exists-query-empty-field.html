exists 查询与空字段判断

真实索引5种不同空值状态的文档，验证exists查询把空字符串判定为存在、把没写字段/null/空数组统一归为不存在的真实规则，这跟业务代码里对这几种空值的语义理解可能完全不一致。

tag值为空字符串''
真实被exists判定为存在
没写字段/null/空数组[]
真实都被exists统一归为不存在
exists判断依据
真实是倒排索引有无词项而非值是否有业务意义

做的事：真实索引5篇文档，tag字段分别设成5种不同的"空"或"有值"状态，用exists查询验证哪些算存在

代码真实索引5篇文档: doc1: {"tag":"active"} ← 正常有值 doc2: {"other_field":"x"} ← 真实压根不写tag这个字段 doc3: {"tag":null} ← 真实显式写了null doc4: {"tag":[]} ← 真实写了一个空数组 doc5: {"tag":""} ← 真实写了一个空字符串 POST /ex_test/_search {"query":{"exists":{"field":"tag"}}}

验证：exists真实只命中了doc1和doc5，空字符串""真实被判定为"存在"

实测 · 本机 Elasticsearch 8.15.0 执行输出 
exists:tag命中结果:
→ doc1 {"tag":"active"}   ← 真实正常有值，命中理所当然
→ doc5 {"tag":""}         ← 真实空字符串也被判定为"存在"！

真实没有命中的: doc2(没写字段)、doc3(null)、doc4(空数组)

这是本文真实最反直觉的发现：空字符串""在业务代码里通常真实被当成"没有有效内容"，但exists查询真实把它判定为字段存在。真实的原因是exists查询底层检查的真实不是"这个值是否有意义"，而是"倒排索引里有没有为这篇文档在这个字段上真实记录过一个token"——空字符串经过分词器处理之后，真实虽然可能不产生任何实际token（取决于字段类型和分词器），但keyword类型字段真实会把空字符串原样当成一个合法的词项索引进去，所以exists真实能查到它。

真实用must_not+exists反过来查，看哪些文档被统一归为"不存在"这一类

代码POST /ex_test/_search {"query":{"bool":{"must_not":{"exists":{"field":"tag"}}}}}

验证：真实没写字段的、null、空数组[]，三种语义完全不同的情况真实被exists统一归成了"不存在"

实测 · 本机执行输出 
must_not exists:tag命中结果:
→ doc2 {"other_field":"x"}   ← 真实压根没写tag字段
→ doc3 {"tag":null}          ← 真实显式写了null
→ doc4 {"tag":[]}            ← 真实写了空数组
这组真实结果完整揭示了exists查询判断"存在"的真实边界：它真实不区分"这个字段压根没在JSON里出现过"、"这个字段显式写了null"、"这个字段是个空数组"这三种在业务语义上完全不同的情况——倒排索引真实对这三种情况都不会记录任何实际的词项，所以exists真实把它们统一当成"不存在"处理。这个真实的归类规则容易在业务代码里造成误解：比如某个字段业务上用null表示"用户主动清空了这个值"、用"没有这个字段"表示"用户从没填过"，这两种真实不同的业务状态在exists查询这里真实没法区分，都会落进must_not exists的结果里；而空字符串""这种"填了但填的是空内容"的状态，反而真实会被判定成"存在"，落进跟真实有值的文档同一组结果里。如果业务上需要精确区分这几种空值语义，不能只依赖exists查询，真实需要在写入层面就做好区分，比如用一个独立的布尔标记字段来显式记录"这个值是否被用户主动清空过"。
