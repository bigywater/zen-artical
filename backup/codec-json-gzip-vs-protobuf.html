压缩过的 JSON 与 Protobuf:谁更小,什么时候该换格式

大家常说“换 Protobuf 就小了”。压缩之后还是这样吗?这篇逐字段拆开看谁赢了哪一列,再把数据模型的改动和格式的改动分开量,看收益到底来自哪里。

855401 对 970854
逐列压缩后合计:JSON 与 Protobuf(2 万条 products,zstd-3)
25.1% 对 11.7%
改数据模型让新 Protobuf 压缩后小的比例,与新模型下 JSON 换成 Protobuf 的收益(zstd-3)
703321 字节
改了数据模型再按列排的 JSON 用 zstd-19 压缩后的大小(原始 JSON Lines 的 9.7%)

逐列比较,Protobuf 只在 stock、seller_id 这类小整数列上压缩后最小;id 这类连续整数,十进制文本反而被压得很干净(JSON 8886 字节,Protobuf 44014 字节);字符串列 JSON 略优(第 3 篇讲过长度前缀的原因)。

先改数据模型

实测 · 本机执行输出 
  一条记录:原模型 JSON 358 字节、新模型 JSON 240 字节;原模型 Protobuf 241 字节、新模型 Protobuf 93 字节
  新模型示例:{"id":1000000,"page":0,"title":"wico biwa wasu kosekefo julomesa zanisa wegiraka","price_cents":11340,"currency":0,"stock":249,"rating10":11,"tags":[53,24,27],"category":19,"updated":1790893697,"seller_id":739,"seller_name":"shop-kujimuge"}

价格存整数分、评分存整数、分类和标签存编号、时间存 Unix 秒、去掉可以由别的字段推出的 url:单条 JSON 从 358 字节降到 240 字节,Protobuf 从 241 降到 93。这些改动与格式无关,JSON 同样受益。

收益来自哪里

实测 · 本机执行输出 
  组合                            原始    zstd-3   zstd-19    gzip-6
  原模型 JSON Lines           7214161   1331194   1047098   1484671
  原模型 Protobuf             4914350   1378051   1081117   1449113
  新模型 JSON Lines           4955536   1169428    927076   1258389
  新模型 Protobuf             2106013   1032452    918732   1042267
  换数据模型的收益(zstd-3):JSON 12.2%、Protobuf 25.1%;换格式的收益(新模型,JSON → Protobuf):原始 57.5%、zstd-3 +11.7%

zstd-3 压缩后,改数据模型让 JSON 小 12.2%、Protobuf 小 25.1%;在新模型下 JSON 换成 Protobuf 只小 11.7%(zstd-19 下只小 0.9%)。换格式的收益比数据模型小。

下限

实测 · 本机执行输出 
  2 万个 title 用换行拼起来 1183715 字节,zstd-3 409620、zstd-19 364005;占新模型 JSON zstd-3 总量 1169428 的 35.0%
  去掉 title 以后:新模型 JSON 634906、新模型 Protobuf 526241(zstd-3 字节),title 单独压缩 409620

title 是随机拼的词,单独压缩要 409620 字节(zstd-3),占新模型 JSON 压缩后总量的 35%。内容本身的熵决定下限,换格式降不下来。

综合

实测 · 本机执行输出

把数据模型改好、按列排布、再用 zstd-19 压缩的 JSON(703321 字节)比任何 Protobuf 变体都小。格式不是体积的决定因素,数据本身的表示、排列和压缩级别才是。如果你要的是类型安全、版本演进、跨语言,Protobuf 仍有它的价值(第 5、6 篇),只是不要指望它自己带来多大的压缩收益。
