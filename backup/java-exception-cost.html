异常真实有多贵:关掉栈追踪只快了 1.3 倍,不是传说中的 10 倍

"异常很贵,主要贵在 fillInStackTrace,关掉栈追踪能快一个数量级"是社区里流传很广的说法。真实计时对比两种异常,把这个数量级到底是多少变成一个具体数字。

怎么关掉栈追踪

Throwable 有一个不常用的构造函数,能在构造时直接跳过栈帧填充。

正常抛异常时,Throwable 的构造函数会调用 fillInStackTrace(),把当前调用栈的每一帧都记录下来。Throwable 还有一个四参数构造函数,最后一个参数 writableStackTrace 设成 false 就能跳过这一步:

StackTraceCost.java(两种异常) static class NormalException extends RuntimeException { NormalException(String msg) { super(msg); } } static class NoStackException extends RuntimeException { NoStackException(String msg) { super(msg, null, false, false); } // cause enableSuppression writableStackTrace }

真实验证:两种异常,50 万次,30 层调用深度

分别独立预热两种异常(各 10 万次),避免共享预热导致 JIT 决策互相干扰,再各自正式计时 50 万次。

两次独立运行的倍数分别是 1.27 和 1.30,结果稳定,但和"关掉栈追踪快一个数量级"这种说法差得很远。真实原因是:抛异常的完整开销不只是 fillInStackTrace 这一步,还包括异常对象本身的分配、throw 触发的栈展开(unwind)、沿着调用链逐层匹配 catch 块——这些开销 writableStackTrace=false 一个都省不掉,它只省了"把每一层栈帧的类名、方法名、行号真实记录下来"这一步。

那这个优化还值得做吗?值得,但预期要真实一些:在异常被大量、高频抛出的场景(比如把异常当控制流用,一秒抛几十万次),省下的 1.3 倍是真实收益,尤其调用栈越深、收益通常越明显;但如果只是常规的错误处理路径(异常本来就应该是低频事件),这点差距在真实系统里几乎感知不到,不值得为了这个把异常语义搞得更复杂。
