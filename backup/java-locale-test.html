时区与 Locale 测试

时区和 Locale 让同一份测试在不同机器上给出不同结果。这篇在真实 JVM 里验证:默认值何时读取、缓存的 Clock、夏令时的缺口与重叠、不同 JDK 版本与本地化数据的输出差别,以及测试应该怎样固定它们。

默认 Locale 的读取时机

实测 · 本机执行输出 
  启动时 Locale.getDefault() = en_US,TimeZone.getDefault() = UTC,user.language = en,user.timezone = UTC
  System.setProperty(user.language=tr, user.country=TR) 之后:Locale.getDefault() = en_US,"title".toUpperCase() = TITLE(没有变化,默认 Locale 在启动时读取并缓存)
  System.setProperty(user.timezone=Asia/Tokyo) 之后:TimeZone.getDefault() = UTC(没有变化)
  Locale.setDefault(tr-TR) 之后:Locale.getDefault() = tr_TR,"title".toUpperCase() = TİTLE,String.format("%.2f", 1234.5) = 1234,50,NumberFormat.getInstance().format(1234.5) = 1.234,5(这些都是在调用时读取默认 Locale,立即生效)
  只设置 Category.FORMAT 为 de-DE:getDefault(FORMAT) = de_DE,getDefault(DISPLAY) = tr_TR,getDefault() = tr_TR,String.format("%.2f", 1234.5) = 1234,50,Locale.FRANCE.getDisplayCountry() = Fransa
  Locale.setDefault(Locale.US) 之后 "title".toUpperCase() = TITLE,String.format("%.2f", 1234.5) = 1234.50
  显式传 Locale 就不依赖默认值:"title".toUpperCase(Locale.ROOT) = TITLE,String.format(Locale.ROOT, "%.2f", 1234.5) = 1234.50,NumberFormat.getInstance(Locale.GERMANY).format(1234.5) = 1.234,5

默认时区、缓存的 Clock 与夏令时

实测 · 本机执行输出 
  默认时区 = Asia/Tokyo:ZoneId.systemDefault() = Asia/Tokyo,LocalDateTime.ofInstant(fixed, ZoneId.systemDefault()) = 2026-10-06T01:30,new Date(fixed).toString() = Tue Oct 06 01:30:00 JST 2026
  默认时区改成 America/Los_Angeles:LocalDateTime.ofInstant(fixed, ZoneId.systemDefault()) = 2026-10-05T09:30;在 UTC 默认时区下创建并缓存的 Clock.systemDefaultZone().getZone() = UTC,用它算出的 LocalDateTime = 2026-10-05T16:30(缓存了旧时区)
  类静态字段 Clock CAPTURED 在 JVM 启动时创建(默认时区 UTC),现在默认时区是 America/Los_Angeles,CAPTURED.getZone() = UTC
  LocalDateTime.now() 用的是调用时的默认时区,现在是几点:LocalDateTime.now().getHour() = 4 时,LocalDateTime.now(CAPTURED).getHour() = 11 时,LocalDateTime.now(ZoneId.of("Asia/Tokyo")).getHour() = 20 时
  夏令时开始(2026-03-08 02:00 → 03:00):ZonedDateTime.of(2026-03-08 02:30 America/New_York) = 2026-03-08T03:30-04:00[America/New_York](不存在的时间被推后 1 小时)
  夏令时结束(2026-11-01 02:00 → 01:00):ZonedDateTime.of(2026-11-01 01:30 America/New_York) = 2026-11-01T01:30-04:00[America/New_York](模糊的时间默认取较早的偏移量),withLaterOffsetAtOverlap() = 2026-11-01T01:30-05:00[America/New_York]
  跨夏令时的加法:2026-03-07 12:00 plusDays(1) = 2026-03-08T12:00-04:00[America/New_York],plusHours(24) = 2026-03-08T13:00-04:00[America/New_York],Duration.between(d0, d0.plusDays(1)) = 23 小时
  一天的长度:2026-03-08 在 America/New_York 有 23 小时,2026-11-01 有 25 小时
  SimpleDateFormat 使用默认时区(现在是 America/Los_Angeles):2026-10-05 09:30 PDT;另一个 SimpleDateFormat 在创建之后 TimeZone.setDefault(UTC)(已创建的实例不受影响):
      原来那个 sdf 仍然格式化为 2026-10-05 09:30 PDT,新建的 SimpleDateFormat 格式化为 2026-10-05 16:30 UTC
