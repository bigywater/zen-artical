编码识别:Content-Type、meta、chardet 谁说了算,乱码从哪来

爬虫拿到的网页乱码,往往不是页面坏了,而是你和服务器对“这段字节是什么编码”有不同的答案。这篇用本机服务器逐一复现:响应头、meta、实际字节三者不一致时 requests 和 lxml 分别怎么选,猜编码的库有多准。

requests 的 r.encoding 来自响应头;text/* 类型没写 charset 时是 ISO-8859-1,于是 UTF-8 页面成了乱码,尽管 r.apparent_encoding 已经猜出了 utf-8。非 text/* 类型(如 application/octet-stream)的 r.encoding 是 None,r.text 反而会用猜测值。requests 不读 HTML 里的 <meta charset>,lxml 解析字节时读 meta、不看响应头。

响应头与实际字节不一致时 r.text 乱码;而用 lxml 解字节、页面有 meta 时能解对。GB2312 的字符集比 GBK 小:页面声明 gb2312 但包含“镕”这样的 GBK 字符,Python 的 gb2312 解码会把它替换掉,lxml 则在该字符处截断了后面的内容。把声明为 gb2312 的页面当 gbk 或 gb18030 解码更安全。

怎么修

实测 · 本机执行输出 
  默认 r.text → 'ç\x88¬è\x99«å·¥ç¨\x8b:ç¼\x96ç\xa0\x81è'
  r.encoding = r.apparent_encoding('utf-8') 之后 → '爬虫工程:编码识别示例,中文网页常见的 '
  自己对字节解码 r.content.decode("utf-8") → '爬虫工程:编码识别示例,中文网页常见的 '
  交给 lxml 字节(它自己看 meta;这个页面没有 meta)→ 'ç\x88¬è\x99«å·¥ç¨\x8b:ç¼\x96ç\xa0\x81è'
  把 r.text(字符串)交给 lxml,如果文档带 XML 编码声明 → ValueError: Unicode strings with encoding declaration are not supported.

最直接的办法:自己对 r.content 解码(比如先试 utf-8,失败再试 gb18030),或把 r.encoding 设成 r.apparent_encoding。给 lxml 传字节而不是字符串,但页面没有 meta 时它也会乱码;给 lxml 传字符串且文档带 XML 编码声明会抛 ValueError。

UTF-8 BOM

实测 · 本机执行输出 
  响应体以 BOM 开头:r.encoding='utf-8',r.text 的前 3 个字符 '\ufeff<h'(\ufeff 是 BOM),r.content.decode("utf-8-sig")[:3]='<ht'

响应体开头的 BOM 在 utf-8 解码后变成 \ufeff 字符,留在 r.text 开头;用 utf-8-sig 解码才会去掉。
