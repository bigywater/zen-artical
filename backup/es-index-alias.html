Index Alias 与直接访问索引的差异

真实把一个alias同时指向两个索引，验证写入时的歧义拒绝、is_write_index如何消歧，以及读取操作为什么完全不受这层限制影响。

做的事：真实让一个alias同时指向两个索引，测试读和写两种操作

代码POST /_aliases {"actions": [ {"add": {"index": "alias_idx1", "alias": "multi_alias"}}, {"add": {"index": "alias_idx2", "alias": "multi_alias"}} ]} POST /multi_alias/_doc {"a": 2} # 往这个alias写一条新文档 GET /multi_alias/_search # 从这个alias读数据

验证：写入一个指向多个索引的alias，真实直接400报错

实测 · 本机 Elasticsearch 8.15.0 执行输出 
POST /multi_alias/_doc {"a": 2}
→ 400 illegal_argument_exception:
  "no write index is defined for alias [multi_alias]. The write index may be
   explicitly disabled using is_write_index=false or the alias points to
   multiple indices without one being designated as a write index"

这是真实合理的设计：如果一个alias真实同时指向两个索引，ES没有办法替调用方决定"这条新文档到底该写进哪一个"，与其悄悄挑一个（可能是别的系统依赖的顺序，不稳定也不可控），ES真实选择直接拒绝这次写入，把这个决定权交还给调用方——不管写入时有没有显式指定文档ID，这条规则真实都一视同仁地生效。

验证：显式指定is_write_index之后，写入真实成功并精确路由到了那个索引

实测 · 本机执行输出 
POST /_aliases {"actions": [
  {"add": {"index": "alias_idx1", "alias": "multi_alias", "is_write_index": true}}
]}

POST /multi_alias/_doc {"a": 2}
→ {"_index": "alias_idx1", "result": "created", ...}   ← 真实写进了alias_idx1
这组真实结果给出了多索引alias支持写入的正确方式：给其中一个成员索引显式标记is_write_index: true，真实消除了"该写进哪一个"的歧义，之后所有对这个alias的写入都会真实精确路由到这个被指定的索引，另一个索引（alias_idx2）真实只作为只读的查询目标存在。这正是ES官方推荐的"滚动索引"（rollover）模式的真实基础：一个应用层永远只认一个alias名字去写数据，底层真实可以把is_write_index随时切换到一个新建的索引上，应用代码完全不需要感知到索引名字本身已经变了——本系列后面会专门验证Rollover如何借助这个机制自动创建新索引。

验证：读操作完全不需要write_index这层限制，真实能同时查到所有成员索引的数据

实测 · 本机执行输出 
alias_idx1里有一条{"a":2}，alias_idx2里有一条{"a":3}

GET /multi_alias/_search {"query":{"match_all":{}}}
→ hits.total = 2
  alias_idx1: {"a": 2}
  alias_idx2: {"a": 3}
真实两条数据都被搜到了，尽管只有alias_idx1被标记成了write_index

这是本文认为这篇最该记住的真实结论：write_index这个限制只影响写入，完全不影响搜索——查询一个多索引的alias，ES真实会把它当成对所有成员索引做一次跨索引的联合搜索，不管这些索引里哪个被标记成了write_index，数据都真实会被同时检索到。应用代码用alias而不是直接用索引名字访问数据的真实价值正在于此：读写双方都通过同一个稳定的alias名字操作，底层真实有多少个索引、哪个在接收新数据、哪个只是历史数据的只读分区，这些细节对使用alias的代码完全透明。
