窗口缩放选项:为什么 64 KiB 不够

为什么 64 KiB 的窗口不够用?窗口缩放选项到底把窗口放大了多少?macOS 的接收缓冲区自动调整多久把窗口放大到上限,上限又怎样决定吞吐?这篇用握手里的真实选项、100 ms 往返的回环传输和真实公网的 RTT 来回答。

41.8 MB/s
往返 100 ms 的回环上,接收窗口自动放大到 4 MiB 上限后的稳定吞吐(= 4,194,240 ÷ 0.1 s)
s = 6 与 s = 13
本机和 example.com 在握手里协商的窗口缩放移位数(最大窗口 4,194,240 与 536,862,720 字节)
0.27 MB/s
不缩放时到 example.com(RTT 243 ms)的吞吐上限;缩放之后上限 17 MB/s

  没有窗口缩放(s = 0)时,窗口最大 65535 字节:RTT 100 ms 的链路上吞吐最多 0.66 MB/s ≈ 5.2 Mbit/s,不管带宽多大;窗口缩放让这个上限随 s 指数增长。选项只出现在 SYN / SYN-ACK 里,而且 SYN 里的窗口字段本身不缩放

窗口字段 16 位,选项里的移位数 s 把窗口扩大到 2^s 倍(最大 s = 14,约 1 GiB)。

  两边各有各的移位数,互不影响;要启用缩放,SYN 和 SYN-ACK 里都必须带窗口缩放选项,只有一边带的话两边都不缩放

选项只在 SYN / SYN-ACK 里协商,双方各有自己的 s:本机 6,example.com 13。

  窗口(缓冲区)随着传输进行自动长大,吞吐随之上升:内核根据"最近一个 RTT 内收到了多少数据"来放大接收缓冲区,上限是 net.inet.tcp.autorcvbufmax(4 MiB)

macOS 默认开启接收缓冲区自动调整,约 1 秒内把窗口放大到 autorcvbufmax(4 MiB);之后吞吐由窗口 ÷ RTT 封顶。

不缩放的代价

实测 · 本机执行输出 
  到example.com:connect 耗时(≈ 一个 RTT)中位 243 ms:不缩放时 65535 字节窗口 ÷ RTT = 0.27 MB/s ≈ 2.2 Mbit/s;缩放 2^6 时本机能通告的窗口 4,194,240 字节 → 上限 17 MB/s
  到另一个公网主机:connect 耗时(≈ 一个 RTT)中位 293 ms:不缩放时 65535 字节窗口 ÷ RTT = 0.22 MB/s ≈ 1.8 Mbit/s;缩放 2^6 时本机能通告的窗口 4,194,240 字节 → 上限 14 MB/s
  缩放选项几乎是必须的:今天的链路动辄 100 Mbit/s 以上、RTT 几十到几百毫秒,不缩放的 64 KiB 窗口会把带宽浪费掉绝大部分

往返 200~300 ms 的链路上,64 KiB 窗口只有 0.2~0.3 MB/s,与带宽无关。
