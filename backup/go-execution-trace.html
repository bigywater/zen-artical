执行追踪 go tool trace:goroutine 在哪里等了多久

CPU profile 看不到 goroutine 在等什么。执行追踪记录每个 goroutine 的阻塞、唤醒、调度,可以回答“它在哪里等了多久”。这篇不用网页界面,用命令行把 trace 导成 pprof 和事件文本,并用程序自己的计时校验 trace 给出的数字。

314.33 ms
4 个 goroutine 争锁时,trace 的 sync 阻塞 profile 归到 Mutex.Lock 的等待
4690 vs 1906 ms
20 个 goroutine 排队:程序自己量到的排队时间对 sched profile 的总量(单次运行)
+22%
开着 trace 时,分配密集的小程序耗时增加
← 上一篇 block 与 mutex profile:锁等待是怎么被记录的

go tool trace -pprof=sync 把 goroutine 阻塞在同步原语上的时间按调用栈汇总。4 个 goroutine 争锁的例子里,Mutex.Lock 记了 314.33 ms、归到 main.holdLock;另外混进了运行时自己的 goroutine 的 100 ms(traceStartReadCPU),读这类结果要认得哪些是运行时内部的项。

20 个 goroutine 在一个 P 上排队,程序自己量出来的排队时间是 4690 ms,而 -pprof=sched 的总量只有 1906 ms(另外几次是 804、1353 ms)。为什么偏小又不稳定,我没有查清。把它当作“哪个栈等得多”的相对排序用,不要当作精确的总时间。

代价

实测 · 本机执行输出 
  plain  :耗时 最小 0.040 s / 中位 0.041 s / 最大 0.042 s
  traced :耗时 最小 0.048 s / 中位 0.050 s / 最大 0.050 s;trace 文件 0.9–0.9 MB

一个 200 个 goroutine、每个分配 400 次的小程序,开 trace 后中位耗时从 0.041 s 到 0.050 s,约慢 22%,生成 0.9 MB,折合每秒约 18 MB。真实服务的开销取决于事件密度,我只测了这一个例子。

四种命令行 profile

实测 · 本机执行输出 
  execution tracer.
  # Tracing runtime activities
  The execution trace captures a wide range of execution events such as goroutine
  creation/blocking/unblocking, syscall enter/exit/block, GC-related events,
  changes of heap size, processor start/stop, etc. When CPU profiling is active,
  the execution tracer makes an effort to include those samples as well. A precise
  nanosecond-precision timestamp and a stack trace is captured for most events.
  The generated trace can be interpreted using `go tool trace`.
  - net: network blocking profile
  - sync: synchronization blocking profile
  - syscall: syscall blocking profile
  - sched: scheduler latency profile

-pprof= 支持 net、sync、syscall、sched 四种。本文只实验了 sync 与 sched;net 与 syscall 没有试。网页界面(火焰图式的时间线)需要浏览器,这里没有使用。
