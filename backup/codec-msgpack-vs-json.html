MessagePack 比 JSON 小多少,哪些数据几乎没变小

MessagePack 常被说成“更小更快的 JSON”。这篇用 4 个数据集量一量:未压缩和压缩之后各小多少,为什么有的数据几乎没变小,速度比谁快,类型保真和流式读取有什么不同。

11.9% 对 27.1%
未压缩时 MessagePack 比 JSON 小的比例:字符串多的 products 与数值多的 timeseries
+6.2%
products 用 zstd-3 压缩后,MessagePack 比 JSON 反而大的比例
13.7 对 5.0 ms
products 打包:msgpack 与 orjson 的耗时(标准库 json 是 40.8 ms)

未压缩时 MessagePack 小 11.9%(products)到 27.2%(nested)。但 zstd 压缩之后差距变了:products 上 MessagePack 反而大 6.2%,timeseries 小 15.3%,nested 小 8.2%,含随机二进制的 blobby 基本相同。

为什么差别这么大

实测 · 本机执行输出 
  products:MessagePack 逐值统计合计 6357305 字节(整批打包 6357308 字节,差在数组头);字符串 64.8%;键名 25.5%;浮点 5.7%;整数 3.1%;容器头 0.9%
  timeseries:MessagePack 逐值统计合计 2000000 字节(整批打包 2000003 字节,差在数组头);键名 57.5%;浮点 22.5%;整数 17.5%;容器头 2.5%
  products:JSON 7214163 → MsgPack 6357308,省下 11.9%;timeseries:2744543 → 2000003,省下 27.1%

字符串多的数据(products 字符串占 64.8%),MessagePack 没什么可省;数值多的数据(timeseries 键名 57.5%、浮点和整数共 40%)省得多。数字越多,受益越大。

速度

实测 · 本机执行输出 
  products:json.dumps 40.8 ms;orjson.dumps 5.0 ms;msgpack.packb 13.7 ms;json.loads 45.0 ms;orjson.loads 21.7 ms;msgpack.unpackb 32.9 ms
  timeseries:json.dumps 25.2 ms;orjson.dumps 3.3 ms;msgpack.packb 8.7 ms;json.loads 25.4 ms;orjson.loads 10.5 ms;msgpack.unpackb 16.3 ms

msgpack 比标准库 json 快(打包约 3 倍),但比 orjson 慢。“二进制就是快”不成立,要看对比的是哪个 JSON 实现。

  use_bin_type=False(旧格式):bytes 和 str 打包成同一类型 → {'a': 'ab', 'b': 'ab'}
  默认 strict_map_key=True 解包整数键:ValueError

MessagePack 比 JSON 多了 bytes 和整数键(解包要 strict_map_key=False),tuple 会变成 list,2^64 溢出,datetime 和 set 要自己处理。bytes 和 str 的区分需要 use_bin_type=True。

  把流截断在中间(多出半条):Unpacker 取出 1001 条完整记录,最后半条不会报错,只是留在缓冲里(再喂剩下的字节就能取出)

每个 MessagePack 值自带长度,多条记录直接拼接,用 Unpacker 分块喂入就能取出(实验里 2000/2000)。JSON Lines 靠换行分隔。被截断的最后半条,Unpacker 不报错,只是还不能取出。

为什么压缩后反而更大

实测 · 本机执行输出 
  版本                                      JSON   MsgPack  zstd JSON   zstd Msg    MsgPack 比 JSON(压缩后)
  原样(price/rating 是浮点)                 7214163   6357308    1331144    1413136                  +6.2%
  price→整数分、rating→整数                  7176128   6077249    1336116    1388457                  +3.9%
  去掉 price 和 rating                    6675704   5737308    1208518    1280003                  +5.9%
  参考:1000 个 price 的 8 字节 float64 二进制(拼接)zstd-3 后 3732 字节(原 8000 字节);同样 1000 个 price 的文本(逗号分隔)zstd-3 后 2619 字节(原 5921 字节)
  只看字符串字段(把某个字段的 2 万个值单独拿出来):
    title      JSON 数组  1223717 → zstd  413803;MsgPack 数组  1203160 → zstd  436587;换行分隔的纯文本  1183715 → zstd  409620
    url        JSON 数组  1135001 → zstd   11989;MsgPack 数组  1115003 → zstd   12386;换行分隔的纯文本  1094999 → zstd   12331
    updated_at JSON 数组   460001 → zstd  100143;MsgPack 数组   420003 → zstd   99373;换行分隔的纯文本   419999 → zstd   99436
    category   JSON 数组   451749 → zstd   35091;MsgPack 数组   411751 → zstd   35938;换行分隔的纯文本   411747 → zstd   34720

检验了两个猜想:浮点的 8 字节二进制压得差一些,但去掉浮点字段后 MessagePack 仍然大 5.9%,所以不是主因;长度不一的 title 字符串单独压缩时,MessagePack 数组比 JSON 数组大 5.5%,长度一致的 url 就没有差别。我的解释是字符串长度前缀是每条都要单独存的信息,而 JSON 的结束引号更好预测,这个解释没有拆到压缩器内部验证。
