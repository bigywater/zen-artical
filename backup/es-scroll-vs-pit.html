Scroll 与 Point In Time 的区别

真实验证scroll_id在API结构上绑定了打开那一刻的具体查询、无法中途切换，重用较早scroll_id也不会倒回旧位置，并对比PIT作为解耦自查询的独立快照引用可以灵活配合任意不同查询使用。

scroll续传接口
真实结构上没有query字段，无法换查询
重用较早的scroll_id
真实不倒回旧位置，从当前游标继续
同一个pit id配合不同查询
真实都能成功执行并保持快照一致

做的事：真实检查/_search/scroll续传接口能传哪些参数，看它能不能换一条不同的查询继续跑

代码真实索引5000条文档 POST /spv_test/_search?scroll=1m {"size":100,"query":{"match_all":{}},"sort":["_doc"]} → 真实拿到第一个scroll_id POST /_search/scroll {"scroll":"1m","scroll_id":"<上一步的scroll_id>"} ← 真实这个续传接口的请求体里只有scroll和scroll_id两个字段，没有query

验证：scroll_id真实绑定的是打开那一刻的具体查询，续传接口在结构上就不接受新的query

实测 · 本机 Elasticsearch 8.15.0 执行输出 
/_search/scroll的真实请求体结构:
→ {"scroll":"1m","scroll_id":"..."}
  ← 真实没有query字段这个选项，想传也没地方传

这个真实的API结构差异直接揭示了scroll的设计本质：scroll_id真实不是一个"可以搭配任意查询使用的快照句柄"，它真实是"某一条具体查询在某个时刻执行结果"的延续凭证——打开scroll的时候传的query条件真实已经被固化进了这个scroll_id背后的搜索上下文里，后续的/_search/scroll调用真实只是在问"这条已经在跑的查询，下一批结果是什么"，没有办法中途换一个完全不同的过滤条件继续用同一个scroll会话。

真实验证一个容易被误解的细节：重新用一个"较早"的scroll_id，会不会真的退回到更早的那个位置

代码POST /spv_test/_search?scroll=1m ... → 真实拿到scroll_id_A POST /_search/scroll {"scroll_id": scroll_id_A} → 真实取到n=100-199，返回新的scroll_id_B 真实再用"更早"的scroll_id_A重新请求一次: POST /_search/scroll {"scroll_id": scroll_id_A}

验证：重新用较早的scroll_id真实没有报错也没有倒回去，而是从当前位置继续往后取

实测 · 本机执行输出 
用已经用过一次的"较早"scroll_id_A再请求一次:
→ 真实没有报错，返回了n=200到n=299这一批（不是重新倒回到n=0-99）
这个真实结果纠正了一个容易产生的误解：scroll_id字符串本身真实不是一个可以用来"回退"的固定书签，它背后对应的是服务端一个持续向前推进的游标状态——不管调用方手里拿着哪一代scroll_id字符串，真实只要这个底层搜索上下文还活着，请求真实都是"从当前游标位置继续往后取"，而不是"回到生成这个scroll_id字符串那一刻的位置"。这跟接下来对比的PIT行为形成了真实鲜明的反差。

真实验证PIT跟scroll的根本不同：同一个pit id能不能配合两条完全不同的查询分别使用

代码POST /spv_test/_pit?keep_alive=1m → 真实拿到pit id POST /_search {"query":{"range":{"n":{"lt":10}}},"pit":{"id":"<同一个pit id>"},"sort":[{"n":"asc"}]} POST /_search {"query":{"range":{"n":{"gte":4990}}},"pit":{"id":"<同一个pit id>"},"sort":[{"n":"asc"}]}

验证：同一个pit id真实可以配合两条完全不同的查询分别使用，结果真实都停留在同一个冻结快照内

实测 · 本机执行输出 
查询1(n<10): hits = [0, 1]
查询2(n>=4990，跟查询1完全不同的过滤条件): hits = [4990, 4991]
  ← 真实两条内容完全不同的查询，都成功用了同一个pit id

这组真实对比完整地回答了"scroll和PIT到底有什么本质区别"：scroll_id真实是"查询+快照"绑在一起的一次性凭证，续传接口结构上就不支持换查询，而且reuse旧字符串真实也不会倒回旧位置；pitid真实只是一个单纯的"冻结读取视图"引用，不携带任何具体查询信息，可以真实像本系列第52篇验证过的那样，搭配search_after做增量翻页，也可以真实像本次这样，直接配合任意不同的query条件分别使用，返回结果都真实保证来自同一个打开那一刻的数据快照。这也是为什么新版本ES把"深分页/完整遍历"的推荐方案从scroll迁移到了PIT+search_after——PIT把"快照一致性"这个关注点，真实从"和一条具体查询强绑定"解耦成了一个可以灵活复用的独立资源。
