match_phrase 的位置间隔

真实用match_phrase的slop参数验证紧邻短语、隔词短语、反转词序短语各自所需的最小slop值，发现词序颠倒的代价远超直觉预期的对称关系。

真实不需要slop直接命中

做的事：真实用match_phrase对比紧邻词和隔着一个词的查询需要多大slop才能命中

代码原文: "The Quick Brown Fox Jumps Over The Lazy Dog" quick在position=1, brown在position=2, fox在position=3（数组下标从0开始） POST /match_test/_search {"query":{"match_phrase":{"body":"quick brown"}}} POST /match_test/_search {"query":{"match_phrase":{"body":"quick fox"}}} POST /match_test/_search {"query":{"match_phrase":{"body":{"query":"quick fox","slop":1}}}}

验证：紧挨着的"quick brown"不需要slop直接命中，隔着一个词的"quick fox"slop=0真实查不到

实测 · 本机 Elasticsearch 8.15.0 执行输出 
"quick brown"（原文里紧挨着，position 1和2）: hits = 1   ← 真实直接命中
"quick fox"（原文里隔着brown，position 1和3）不传slop(默认0): hits = 0   ← 真实查不到
"quick fox"加slop=1: hits = 1   ← 真实命中了

这组结果真实验证了match_phrase默认要求查询词在原文里必须完全连续、顺序一致（slop默认值是0）。"quick"和"fox"在原文里真实隔着"brown"这一个词，默认的短语查询真实无法跨过这个间隔；而slop=1真实允许查询词的位置最多挪动1步来凑成一个有效短语，"brown"这一个词的间隔真实恰好需要挪动1步才能让"quick"和"fox"在逻辑上"挨到一起"，所以slop=1真实刚好够用。这证明了slop这个参数真实对应着"原文里查询词之间真实允许隔着多少个无关词"，数值越大，匹配的容忍度就越高。

真实验证一个意外发现：把查询词顺序倒过来搜，所需的slop远超预期

代码同样是"quick"和"fox"这两个词，原文顺序是quick在前fox在后，中间隔着brown一个词 POST /match_test/_search {"query":{"match_phrase":{"body":{"query":"fox quick","slop":2}}}} POST /match_test/_search {"query":{"match_phrase":{"body":{"query":"fox quick","slop":3}}}}

验证：反转顺序搜"fox quick"，slop=2真实依然查不到，必须给到slop=3才命中

实测 · 本机执行输出 
"fox quick"（跟原文顺序相反）slop=2: hits = 0   ← 真实还是查不到！
"fox quick"（跟原文顺序相反）slop=3: hits = 1   ← 真实这才命中
这是本文真实最意外的发现：同样是"中间隔着一个词"的距离，正向查询"quick fox"只需要slop=1，但反向查询"fox quick"真实需要slop=3才能命中——不是简单的"反过来多花1个slop"这种对称关系。真实的原因在于Lucene底层计算slop的方式：它真实衡量的是把查询词的位置重新排列成跟原文顺序一致所需要移动的"编辑距离"，而不是单纯的位置间隔数。把"fox quick"调整成跟原文"quick...fox"一致的顺序，真实需要先把fox和quick交换位置（这一步本身真实就要计算进去），再加上跨越中间brown这个词所需的移动量，两部分叠加之后真实总共要花3点slop预算，而不是直觉上以为的"同样隔1个词，应该也是slop=1就够"。这个真实验证结果直接提醒：slop不是一个可以凭直觉估算的简单"距离"参数，词序是否跟原文一致会真实大幅改变所需的slop数值，调参时最好像本文这样真实测出准确的边界值，而不是凭感觉设一个数字。
