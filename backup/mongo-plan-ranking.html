查询计划竞选:候选计划各试跑多少文档

候选计划各试跑多少文档?谁来决定赢家?这篇用 allPlansExecution 看每个候选的 nReturned 和 works,改参数看试跑如何缩短,并验证排序阻塞和结果很少时的情形。

101
每个候选计划试跑最多取的结果数(internalQueryPlanEvaluationMaxResults 默认值)
101 对 1
同样 101 次 works 里,b_1 与 a_1 候选各返回的条数
0.3 ms
不 hint 时优化器选中的 b_1 的实际耗时(c_1 是 135 ms)
← 上一篇 唯一索引遇到 null 和缺失字段

一条查询有多个候选索引时,每个候选计划试跑一小段,看同样的 works 里谁返回的结果更多。b_1 返回 101 条而 a_1 只返回 1 条,所以 b_1 赢。

试跑的上限

实测 · 本机执行输出 
  test> db.adminCommand({getParameter: 1, internalQueryPlanEvaluationMaxResults: 1, internalQueryPlanEvaluationWorks: 1, internalQueryPlanEvaluationCollFraction: 1, internalQueryCacheEvictionRatio: 1, internalQueryCacheWorksGrowthCoefficient: 1})
  {
    internalQueryCacheEvictionRatio: 10,
    internalQueryCacheWorksGrowthCoefficient: 2,
    internalQueryPlanEvaluationCollFraction: 0.3,
    internalQueryPlanEvaluationMaxResults: 101,
    internalQueryPlanEvaluationWorks: 10000,
    ok: 1
  }

由参数控制:最多取 101 条结果(internalQueryPlanEvaluationMaxResults)、最多 10000 次 works,或不超过集合的 30%。

把 MaxResults 调成 10,试跑在第一个计划返回 10 条时结束,其它候选陪跑到同样的 works。

内存 SORT 要读完所有输入才会输出第一条,试跑期间返回 0 条;按索引顺序扫的计划边扫边出结果,在竞选里更占便宜。

某个计划几次 works 就把所有结果返回完,试跑立刻结束,它直接获胜。

验证

实测 · 本机执行输出 
  hint(a_1): 16 ms
  hint(b_1): 0.5 ms
  hint(c_1): 135 ms
  不 hint(优化器选): 0.3 ms

逐个 hint 的完整耗时是 16 / 0.5 / 135 ms,优化器自己选的 0.3 ms,选中了最快的计划。
