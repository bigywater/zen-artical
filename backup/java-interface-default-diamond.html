接口默认方法菱形冲突真实验证:不显式覆盖，编译器真实直接拒绝编译

Java 8引入接口默认方法后，一个类同时实现两个都定义了同名默认方法的接口会怎样？这篇真实构造这种菱形冲突场景，验证编译器的真实反应，以及正确的显式覆盖语法。

真实复现:菱形冲突下不覆盖，编译器真实直接拒绝

接口A和接口B互不相关，各自定义了默认实现的greet()方法，类C同时实现两者但不覆盖greet()，真实用javac编译会发生什么。

DiamondErrorDemo.java interface A { default String greet() { return "A"; } } interface B { default String greet() { return "B"; } } static class C implements A, B { // 故意不覆盖greet() }
真实实测(javac 编译输出) 
DiamondErrorDemo.java:8: error: types A and B are incompatible;
    static class C implements A, B {
           ^
  class C inherits unrelated defaults for greet() from types A and B
1 error

真实结果证明:Java编译器真实不会替你"猜"应该用A还是B的默认实现——这和C++多重继承里那种运行时才暴露的二义性问题不同，Java真实把这个冲突提前到了编译期，直接拒绝编译并给出清晰的错误信息"inherits unrelated defaults"，强制开发者必须显式做出选择。这也是Java为默认方法设计"多重继承实现"时刻意保留的安全边界:接口可以有默认实现，但真实冲突绝不会被静默地按某种隐含优先级自动解决。

真实验证:用X.super.method()语法显式选择或组合

InterfaceDiamondDemo.java static class C implements A, B { @Override public String greet() { return A.super.greet() + " + " + B.super.greet(); } }
真实实测 
真实C.greet()(菱形冲突,显式调用两者): 来自A + 来自B

真实结果证明Java提供了接口名.super.方法名()这个专门语法来解决这个冲突——它让开发者能明确指定"我要调用A这个接口的默认实现"，甚至可以像示例里这样，在覆盖版本里同时调用A和B两个版本并组合它们的结果。这个语法只能在实现类内部使用，且只能指向类直接实现的接口，不能跳过中间层级。

真实验证:接口存在真实父子关系时，无需显式覆盖

InterfaceDiamondDemo.java interface Base { default String hello() { return "Base"; } } interface Sub extends Base { default String hello() { return "Sub"; } } static class D implements Base, Sub { // 不需要覆盖 }
真实实测 
真实D.hello()(子接口默认方法自动胜出): Sub
真实规则的关键在于"是否存在真实的继承关系"，不是"是否同时被实现"。类D同时实现了Base和Sub两个接口，表面上和前面的菱形冲突场景很像，但真实结果证明编译器没有报错，而是自动选择了更具体的Sub.hello()——因为Sub extends Base，两者之间存在明确的"谁更具体"的关系，JLS规定这种情况下更具体的接口默认方法真实自动胜出，不需要开发者介入。只有当两个接口之间没有继承关系(像前面的A和B)时，编译器才无法判断优先级，才会真实报错要求显式解决。这个细节容易被简化成"实现多个接口有同名默认方法就会冲突"，但真实规则比这精确得多:只有互不相关的接口之间的冲突才会真实拒绝编译。
