Rust 项目持续集成

CI 就是把本地的检查命令放到一个每次提交都会跑的地方。这篇写了一个完整的 ci.yml,然后诚实地区分:哪些是真正验证过的(语法检查、命令本身、门禁行为),哪些只能在 GitHub 上运行才知道(这篇没有做)。

注入的 4 种缺陷各只让对应的 1 个 job 失败

矩阵展开

实测 · 本机执行输出 
  触发条件: {'push': {'branches': ['main']}, 'pull_request': None}
  test 矩阵:os × toolchain = 2 × 2 = 4 个 job: ubuntu-latest/stable, ubuntu-latest/beta, macos-latest/stable, macos-latest/beta
  整个工作流一次触发的 job 数:fmt 1 + clippy 1 + test 4 + audit 1 = 7;audit 声明 needs = ['fmt', 'clippy', 'test'](要等前面的 job 成功);test 里 fail-fast = False
  每个 job 的 run 步骤:
    fmt: ['cargo fmt --all -- --check']
    clippy: ['cargo clippy --locked --all-targets -- -D warnings']
    test: ['cargo build --locked', 'cargo test --locked']
    audit: ['cargo install cargo-audit --locked', 'cargo audit']

    本文用到的工具与边界

    • 本机 macOS 27 arm64 / rustc 1.98.1(brew)/ cargo 1.98.1;单个文件用 rustc 直接编译,需要依赖时用 cargo(经代理从 crates.io 下载);计时用 std::time::Instant,数字每次运行会有小幅抖动。actionlint 1.7.12(go install);PyYAML 6.0.2;cargo-audit 0.22.2(RustSec 漏洞库)
    • 没有验证:工作流在 GitHub Actions 上的真实运行(runner、权限、secrets、并发、超时)、uses: 的第三方 action(actions/checkout@v4、dtolnay/rust-toolchain、actions/cache@v4)的行为、beta 工具链与 ubuntu runner 上的结果、hashFiles 的实际算法、真实缓存的命中与大小限制、其它 CI 系统(GitLab CI 等)
    • 本机执行时跳过了 uses: 与 cargo install 步骤,test 只跑了一个矩阵项,所以「本机通过」不能代替 CI 的结果
