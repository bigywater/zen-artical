聚合内存占用与 Circuit Breaker

真实用30万个唯一UUID验证terms聚合超过默认65536桶上限时被精确拒绝，低于上限的请求正常执行，并通过临时调低search.max_buckets到1000证明这个聚合内存保护阈值完全可配置且精确生效。

真实成功执行，确认65536是精确分界线
调低阈值到1000

做的事：真实对30万个唯一UUID的字段跑terms聚合，size直接设成300000想把全部唯一值一次性拉出来

代码真实索引300000条文档，uid字段真实是300000个互不相同的UUID POST /cb_test/_search {"size":0,"aggs":{"t":{"terms":{"field":"uid","size":300000}}}}

验证：请求真实直接被拒绝，报错精确写出了65536这个默认的桶数量上限

实测 · 本机 Elasticsearch 8.15.0 执行输出 
→ 400 too_many_buckets_exception:
  "Trying to create too many buckets. Must be less than or equal to:
   [65536] but this number of buckets was exceeded. This limit can be
   set by changing the [search.max_buckets] cluster level setting."

这条真实报错揭示了search.max_buckets这个专门为了防止聚合把内存耗尽而设的保护阈值（本系列第70、78篇都分别验证过相关的硬编码上限，这是聚合层面类似的真实保护机制）。每一个聚合桶在服务端真实都需要维护计数器、子聚合状态等内存结构，一次性请求几十万个桶，真实会让这部分内存开销失控地膨胀，所以ES真实从请求校验阶段就直接把超出65536这个默认上限的请求拦截掉，而不是真的去尝试分配内存、等到内存真的耗尽才报错。

真实把size收窄到60000（低于默认上限），验证能否成功跑出接近上限数量的桶

代码POST /cb_test/_search {"size":0,"aggs":{"t":{"terms":{"field":"uid","size":60000}}}}

验证：60000个桶的请求真实成功了，确认65536是精确的分界线而不是模糊限制

实测 · 本机执行输出 
→ 请求真实成功，bucket count: 60000

这个真实结果确认了65536这个数字是一条精确的硬性分界线：低于它的请求（本次60000）真实能正常执行完成，超过它的请求（前面的300000）真实会被直接拦截。

真实把search.max_buckets临时调低到1000，验证这个阈值是不是真的可配置、精确生效

代码PUT /_cluster/settings {"persistent":{"search.max_buckets":1000}} POST /cb_test/_search {"size":0,"aggs":{"t":{"terms":{"field":"uid","size":5000}}}}

验证：调低阈值之后，同样5000个桶的请求真实立刻被拒绝，报错里的数字精确变成了新设的1000

实测 · 本机执行输出 
→ too_many_buckets_exception:
  "Must be less than or equal to: [1000] but this number of buckets was exceeded"
  ← 真实报错里的数字精确对应刚刚配置的1000，不再是默认的65536
这组真实验证证明了search.max_buckets真实是一个完全可配置、精确生效的集群级保护参数，不是写死在代码里的黑盒常量——调低到1000之后，原本在默认配置下完全正常的5000个桶请求真实立刻被拦截，报错信息里的数字真实精确跟随配置变化。这提醒了真实运维这类保护阈值时的双重考量：阈值设得太低，会真实误伤本来合理的大规模分析类查询（比如按天统计一年的数据，加上多个维度交叉可能真实需要几千上万个桶）；阈值设得太高或者干脆不设限制，又真实失去了防止聚合请求意外耗尽集群内存的保护作用。真实遇到这类保护机制拦截时，正确的应对思路通常不是粗暴调大阈值，而是真实检查业务上是不是真的需要一次性取回这么多桶——本系列第78篇验证过的composite聚合分页正是为这种"真实需要遍历海量桶但又不想触碰这个保护上限"的场景设计的标准方案。
