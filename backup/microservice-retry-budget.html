重试预算:限制重试占总请求的比例

重试预算怎么限制“重试占总请求的比例”?它在失败率低的时候会不会妨碍重试?在多层叠加时能把放大压到多少?这篇用一个共享令牌桶,在本机的小服务上量出来。

1.099 对 3.000

88.3% / 96.0% / 99.3%

失败率低时预算几乎不妨碍重试;失败率高时放大被压在 1 + ratio 附近,代价是少救回来一些请求。

只有一层重试时放大本来就有限,预算把触发期间多出来的调用压得更少,成功率不变。

多层叠加

实测 · 本机执行输出 
  策略          | C 收到的调用 | 每个原始请求

  每层不限(共 3 次) | 5400    | 27.00 
  每层预算 10%    | 263     | 1.31  
  每层预算 10% 时,放大的上界是每层 1.1 倍,三层是 1.1³ = 1.33;实测值在这附近(桶开始时是空的,所以略低于上界)
  (连接类错误 0 次;不是超时,应为 0)

每层各有预算,放大不再相乘,上限是各层 1 + ratio 的乘积。

    本文用到的工具与边界

    • 本机 macOS 27 arm64 / Python 3.14.8 / Go / nginx / Envoy / etcd / Consul / Nacos / OpenTelemetry / Prometheus(按各篇注明用到哪些及版本);所有服务都是本机自己起的进程,端口 9150 以上,只监听 127.0.0.1,不连任何外部服务,不碰本机已有的实例;故障用 kill -9 进程、让连接断开或在代码里注入延迟与错误来制造;计时用 time.perf_counter,数字每次运行会有小幅抖动。本篇的服务是 Python 3.14 http.server(线程化)在本进程里起的;预算是我写的共享令牌桶(每个原始请求存 ratio 个令牌、桶上限 10、初始为空、每次重试取 1 个),不是任何库的实现;“不限”是每个请求最多共 3 次;第一节每种组合 1500 个请求跑一轮;实验里连接类错误 0 次
    • 没有验证:Finagle / gRPC 的重试节流各自的参数(时间窗口、每秒最少重试数)——这里的桶没有时间衰减;预算在多实例 client 之间不共享时的总放大(每个 client 实例各一个桶);预算与熔断同时使用时的相互作用;更高的并发和真实网络
