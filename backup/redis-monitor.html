MONITOR 的性能代价

MONITOR 是调试利器,也是生产事故的常见来源。这篇量它的两笔代价:吞吐下降多少,以及一个「忘了关的、不读取的」MONITOR 连接会让服务器内存涨到多大。

-34%
一个及时读取的 MONITOR 客户端对管道 SET 吞吐的影响(740k → 485k /s)
78 MB
不读取的 MONITOR 连接,在执行 100 万条命令后占用的输出缓冲
无上限
normal 客户端的 client-output-buffer-limit 默认 0 0 0
← 上一篇 INFO commandstats

吞吐

实测 · 本机执行输出 
  没有 MONITOR:740k 条/秒
  有一个及时读取的 MONITOR 客户端:485k 条/秒(降低 34%)

管道 SET 20 万条,每种情形测 3 次取中位:没有 MONITOR 740k/s,有一个及时读取的 redis-cli monitor 485k/s。这是本机、每条命令很小、单个监控客户端下的数字;命令越多、参数越大,代价越明显。

卡住的 MONITOR:内存无上限

实测 · 本机执行输出 
  CONFIG GET client-output-buffer-limit → normal 0 0 0 slave 268435456 67108864 60 pubsub 33554432 8388608 60
  已执行   200000 条命令:used_memory 比开始时多   15.1 MB,该 MONITOR 连接的 omem =   15.1 MB
  已执行   400000 条命令:used_memory 比开始时多   30.8 MB,该 MONITOR 连接的 omem =   30.8 MB
  已执行   600000 条命令:used_memory 比开始时多   46.6 MB,该 MONITOR 连接的 omem =   46.5 MB
  已执行   800000 条命令:used_memory 比开始时多   62.3 MB,该 MONITOR 连接的 omem =   62.3 MB
  已执行  1000000 条命令:used_memory 比开始时多   78.0 MB,该 MONITOR 连接的 omem =   78.0 MB
  关闭这个连接后 used_memory 比开始多 0.0 MB

我让一个 MONITOR 连接不读取(并把它的接收缓冲调到 4 KB)。CONFIG GET client-output-buffer-limit 里 normal 是 0 0 0——MONITOR 客户端属于 normal 类,没有上限。20 万条命令后它的 omem 是 15 MB,之后线性增长到 100 万条时 78 MB,约 78 字节/条。关掉连接后 used_memory 立刻回到起点。
