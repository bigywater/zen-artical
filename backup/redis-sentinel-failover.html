Sentinel 自动故障转移

Sentinel 的自动故障转移由一串事件组成,每个都有名字(+sdown、+odown、+elected-leader、+promoted-slave、+switch-master……)。这篇订阅 sentinel 的事件流,把一次真实 kill -9 之后的每一个事件和毫秒数都列出来,再从写客户端的角度量不可用时长。

5.3 s
kill -9 主库到 +failover-end 的总时间(down-after-milliseconds = 3000)
约 4.3 s
写客户端(经 sentinel 找主库)不可用的时长
10.2 s
旧主库重启后被 sentinel 改成从库并 link up 所用的时间

阶段:检测(+sdown/+odown)→ 选领导者(+try-failover/+vote-for-leader/+elected-leader)→ 选从库(+selected-slave)→ 发 SLAVEOF NO ONE 并等升主(+promoted-slave)→ 广播新配置(+config-update-from/+switch-master)→ 其它从库改指新主库(+slave-reconf-*)→ 结束(+failover-end)。

客户端看到的

实测 · 本机执行输出 
   新主库地址(sentinel 眼中): ('127.0.0.1', 7741)

一个每 20 ms 经 sentinel 查主库地址再写的客户端:主库被杀 22 ms 后第一次失败,直到新主库可写才恢复。整个不可用窗口里最长的一段是检测(down-after-milliseconds),真正的「选举 + 提升」只占约一秒。

复制拓扑

实测 · 本机执行输出 
  7741: role=master
  7742: role=slave master_port=7741 link=up

最终 7741 是主库,7742 是它的从库并且 link up。

旧主库回来

实测 · 本机执行输出 
  旧主库 7740 重启后 10188 ms:role = slave,master_port = 7741

旧主库重启后,sentinel 把它配置成新主库的从库(重启后一直处于「主库」身份,直到 sentinel 发现并降级);这里用了 10.2 s。这期间旧主库如果被写入,数据会在降级时丢弃(第 91、93 篇)。
