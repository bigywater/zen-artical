PGO:用 profile 引导编译优化,真实能快多少

PGO(profile 引导优化)据说能让程序快 2% 到 14%。这篇自己做一遍:收集 profile、重新编译、看编译器的决定改了什么,然后在五种工作负载上对照运行时间。结果不全是好消息,这正是值得记录的地方。

8.1%
regexp 匹配在 PGO 构建下的提升(471 → 433 ms)
0% 与 -2.0%
其它四种负载的结果:接口调用、直接调用、flate 几乎不变,接口加较长函数的组合慢了 2.0%
146 → 可内联
score 的代价 146 超过默认预算 80,PGO 下在热调用点被内联

没有 profile 时

实测 · 本机执行输出 
  main.go:26:6: cannot inline score: function too complex: cost 146 exceeds budget 80

默认构建下,-gcflags=-m=2 的诊断是:cannot inline score: function too complex: cost 146 exceeds budget 80——函数的内联代价 146,超过了默认预算 80,所以不会被内联。这是后面对照的起点。

profile 就是普通的 CPU profile(runtime/pprof 或 go test -cpuprofile 产生),多个 profile 可以用 go tool pprof -proto 合并。命名为 default.pgo 放在 main 包目录里,go build 默认(-pgo=auto)就会使用;-pgo=off 关闭。这个实验里每个 profile 很小(几百字节到 1.5 KB)——工作负载只跑了不到几秒。

  main.go:46:17: inlining call to score
  main.go:59:41: inlining call to score
  <autogenerated>:1: inlining call to Circle.Area
  <autogenerated>:1: inlining call to Square.Area

从 -m=2 的诊断能直接看到:score 的代价仍是 146,但在 profile 里的热调用点上内联预算被放宽,所以被内联了;接口调用 s.Area() 的热目标也被内联(实现上是在调用点先判断具体类型再直接调用,这是我对“Circle.Area 等被内联”这一诊断的解释,没有读生成的汇编)。

五种负载里只有 regexp 的匹配循环有明显提升(8.1%)。接口调用与直接调用的两个微基准几乎没变,compress/flate 也没变,而同时有接口调用与较长函数的组合反而慢了 2%。我没有去查慢的原因(代码布局、寄存器分配都有可能),只能说:PGO 的收益取决于程序,需要拿自己的负载测,官方给的“几个百分点”不是保证,微基准更容易得到 0。另外这些数字是 arm64 单机上的结果,二进制也略有变大。

默认行为

实测 · 本机执行输出 
  默认 go build 的产物里的构建信息:build	-pgo=<gtmp>/pg1/default.pgo
  -pgo=off 的产物:构建信息里没有 -pgo

因为 -pgo=auto 是默认,往 main 包目录里放一个 default.pgo,所有人构建的结果都会变——所以有这个文件时,要把它当作构建输入对待(纳入版本控制、定期更新),并在 CI 里确认没有性能退化。
