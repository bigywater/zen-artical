upload-pack 的交互:用 GIT_TRACE_PACKET 看 want/have

git clone 和 git fetch 时客户端与服务端到底说了什么?want 和 have 是什么意思?这篇用 GIT_TRACE_PACKET 把 v0 协议的交互全部打出来,再用 upload-pack --advertise-refs 解析原始的 pkt-line 字节。

4 位十六进制
pkt-line 的长度前缀,含自己这 4 个字符;0000 是 flush-pkt
want / have / done
客户端“要什么、已有什么、说完了”的三个动词
399 字节
三个 ref 的 v0 广告(274 + 60 + 61 + 4)总字节数

服务端先开口:每个 ref 一个 pkt-line(<sha> 名字),第一个 ref 后面用 \0 接上 capabilities,最后一个 flush-pkt 0000。客户端用 want <sha> 列出要的提交(第一条带上它选择的 capabilities),0000 结束,done 表示没有更多要说的。新克隆没有共同点,服务端回 NAK,然后在 side-band 里发 pack。

pkt-line

实测 · 本机执行输出 
  偏移 0: 长度 0112(274)→ '<sha> HEAD\\0multi_ack thin-pack side-band side-band-64k ofs-delta shallow deepen-since deepen-not deepen-relative no-progress incl'
  偏移 274: 长度 003c(60)→ '<sha> refs/heads/dev\n'
  偏移 334: 长度 003d(61)→ '<sha> refs/heads/main\n'
  偏移 395: 0000 → flush-pkt
  总共 3 个非空 pkt-line(含 HEAD 一行带 capabilities,其余每个 ref 一行),总字节数 399

每个包前面是 4 位十六进制的长度(包括这 4 个字符本身),0000 是没有内容的特殊包 flush-pkt,表示一段结束。直接调用 upload-pack --advertise-refs 解析原始字节,长度之和正好等于总字节数。

have

实测 · 本机执行输出 
  (只列 want / have / ACK / NAK / done 相关行)
  packet: fetch> want <sha> multi_ack_detailed side-band-64k thin-pack no-progress include-tag ofs-delta deepen-since deepen-not agent=git/2.54.0-Darwin
  packet: fetch> 0000
  packet: fetch> have <sha>
  packet: fetch> done
  packet: fetch< ACK <sha> common
  packet: fetch< ACK <sha>
  fetch 之前对象总数 6,之后 10:新增 4 个对象(1 个 commit、1 个 tree、2 个 blob)

增量 fetch 时客户端用 have 告诉服务端自己已有的提交,服务端回 ACK … common,找到共同点后只打包缺失的对象(本例新增 4 个)。
