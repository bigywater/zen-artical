搜索时 Analyzer 与索引时 Analyzer 不一致的后果

真实配置索引时词干还原、查询时不还原的不对称analyzer，验证这种不一致导致的隐蔽查询失败，并用index-time同义词展开的真实反例说明不一致的后果取决于具体差异点而非一概而论。

索引时stemmer还原
真实把runs/running都存成词干run
查询时不一致的plain分析器
真实导致搜running查不到，搜run反而命中
index-time同义词展开的反例
真实证明查询端不一致不一定会出问题
← 上一篇 停用词过滤器

做的事：真实配一个索引时做词干还原、查询时不做词干还原的不对称analyzer配置

代码PUT /mismatch2 {"settings":{"analysis":{ "filter": {"english_stemmer": {"type":"stemmer","language":"english"}}, "analyzer": { "stem_analyzer": {"type":"custom","tokenizer":"standard","filter":["lowercase","english_stemmer"]}, "plain_analyzer": {"type":"custom","tokenizer":"standard","filter":["lowercase"]} } }},"mappings":{"properties":{ "body": {"type":"text","analyzer":"stem_analyzer","search_analyzer":"plain_analyzer"} }}}} 索引文档: {"body": "the dog runs fast"}

验证：索引时真实把runs还原成了run，查询时plain分析器真实不做任何还原，两者真实对不上

实测 · 本机 Elasticsearch 8.15.0 执行输出 
索引时stem_analyzer对"runs running"分词:
→ ['run', 'run']   ← 两个不同的原始形式真实都被还原成了同一个词干run

查询时plain_analyzer（跟索引用的不是同一个analyzer）对"running"分词:
→ ['running']   ← 真实原样保留，没有做任何词干还原

这组真实的分词结果对比，从根源上展示了analyzer不一致会造成什么样的"错位"：文档写入时，body字段真实用stem_analyzer把"runs"还原成词干"run"存进了倒排索引，索引里压根没有"running"这个原始形式；而search_analyzer被真实配置成了不做词干还原的plain_analyzer，用户搜"running"的时候，这个词真实原样保留，根本不会被还原成"run"去匹配索引里真实存在的词项。

真实验证这个错位的具体后果：搜"running"查不到，搜"run"反而能命中

代码POST /mismatch2/_search {"query":{"match":{"body":"running"}}} POST /mismatch2/_search {"query":{"match":{"body":"run"}}} POST /mismatch2/_search {"query":{"match":{"body":{"query":"running","analyzer":"stem_analyzer"}}}}

验证：搜"running"真实0命中，搜"run"反而真实能命中——纯属字面碰巧一致

实测 · 本机执行输出 
搜"running"（用户真实会输入的自然说法）: hits = 0   ← 真实查不到！
搜"run"（词干形式，用户通常不会这么输入）: hits = 1   ← 真实反而能命中

查询时显式指定analyzer=stem_analyzer（修复了不一致）:
搜"running": hits = 1   ← 真实命中了
这组真实结果最讽刺的地方在于：用户最自然的输入"running"真实查不到，反而是用户几乎不会主动输入的词干形式"run"真实能命中——这完全是运气，"run"这个词干碰巧真实跟plain_analyzer分词后的结果字面一致。这正是analyzer不一致最隐蔽的危害：它不会直接报错，搜索功能看起来"大体上能用"，只是真实会在一些特定词形上莫名其妙地查不到，而且这种失败真实没有任何错误提示，只会让人以为是数据没写进去或者搜索关键词打错了。本次实测用match查询里显式指定analyzer参数覆盖成跟索引时一致的stem_analyzer之后，"running"真实才恢复能查到——这也是真实排查这类问题时最直接的验证手段：用_analyze分别跑一遍索引时和查询时的analyzer，对比两边产出的token是否一致。

真实验证一个反例：index-time同义词扩展的字段，即使search_analyzer不一致，依然可能正常工作

代码index_time_analyzer真实配了同义词过滤器["laptop,notebook"]，search_analyzer故意配成不认识这组同义词的standard 索引文档: {"body": "I bought a new laptop"} POST /mismatch_test/_search {"query":{"match":{"body":"notebook"}}}

验证：哪怕search_analyzer真实不认识这组同义词，搜notebook依然真实命中了

实测 · 本机执行输出 
search_analyzer=standard（真实不包含同义词过滤器）:
搜"notebook": hits = 1   ← 真实依然命中，尽管查询端压根不知道laptop和notebook是同义词

这个真实反例补全了对analyzer不一致后果的完整理解：问题的根源真实不在于"两边analyzer是不是同一个"，而在于"两边analyzer对这个具体查询词的处理结果是否恰好一致"。本次实测里，laptop在索引时真实已经被同义词过滤器同时展开成了laptop和notebook两个并列token存进了倒排索引（本系列第39篇验证过的机制），查询端哪怕完全不认识这组同义词，只要原样把"notebook"当成一个词去查，也真实能在索引里找到这个词项——因为索引端早就真实"提前"把同义关系兑现成了具体的token。这跟前面stemmer的例子刚好相反：stemmer的后果真实只存在于索引端产出的"run"和查询端产出的"running"字面不一致，而同义词展开如果真实发生在索引端，查询端反而可以更"无知"，不需要重复认识同一套规则。
