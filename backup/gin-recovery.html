Recovery 是 defer + recover 加三个分支:判断是不是断管错误、写日志、写响应。普通 panic 交给恢复函数(默认 AbortWithStatus(500));断管错误则只 c.Error 并 Abort,因为连接已经没法再写状态了。

客户端拿到 500 和空正文,没有 Content-Type。日志默认写到 gin.DefaultErrorWriter(标准错误),内容是 panic 值和带源码行的栈,栈里第一帧就是出事的那一行。panic 只影响当前请求,同一个引擎继续服务。

debug 模式的日志会附上请求转储,其中只有 Authorization 头被替换成 *(源码注释写明了“目前只处理 Authorization”),Cookie、X-Api-Key 等头原样输出。线上要用 release 模式(它不输出请求转储),并且别把 debug 日志送进共享的日志系统。

panic 的值

实测 · 本机执行输出 
    收到 err: string → text
    收到 err: *errors.errorString → an error
    收到 err: main.MyErr → {42}
    收到 err: *runtime.PanicNilError → runtime error: panic called with nil argument
    收到 err: runtime.plainError → assignment to entry in nil map
    收到 err: runtime.boundsError → runtime error: index out of range [5] with length 1
    收到 err: runtime.errorString → runtime error: invalid memory address or nil pointer dereference
    收到 err: runtime.errorString → runtime error: integer divide by zero

恢复函数拿到的 err 就是 panic 的原值,可能是字符串、error、你自己的类型,或者各种运行时错误(下标越界、空指针、除零、写 nil map)。panic(nil) 在 Go 1.21 以后会变成 *runtime.PanicNilError,所以 err != nil 的判断不会漏掉它。

自定义恢复与边界

实测 · 本机执行输出 
    /early    → 状态 500 正文 "{\"error\":\"内部错误\",\"id\":\"req-1\"}"      日志里有栈:true  自定义函数累计调用:1 次 c.Errors:0 条
    /late     → 状态 200 正文 "已经写出的前半段{\"error\":\"内部错误\",\"id\":\"req-1\"}" 日志里有栈:true  自定义函数累计调用:2 次 c.Errors:0 条
    /abort    → 状态 200 正文 ""                                           日志里有栈:false 自定义函数累计调用:2 次 c.Errors:1 条
    /epipe    → 状态 200 正文 ""                                           日志里有栈:false 自定义函数累计调用:2 次 c.Errors:1 条
    /wrapped  → 状态 200 正文 ""                                           日志里有栈:false 自定义函数累计调用:2 次 c.Errors:1 条

常见的自定义是返回统一的 JSON 错误体。注意:如果 panic 之前响应已经写出了一部分,状态码改不了,JSON 会拼在已发出的半截正文后面——这种响应是被破坏的,需要在更早的地方避免(先构造完整响应再一次性写出)。断管类 panic 不会调用你的函数,也不记栈。
