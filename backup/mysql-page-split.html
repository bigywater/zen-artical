簇索引页分裂

用同样1000行数据，一份按主键顺序插入一份打乱顺序插入，对比页分裂次数和真实的磁盘空间开销。

14次 vs 19次
顺序插入与乱序插入真实触发的页分裂次数
多约24%空间
乱序插入真实多占用的磁盘空间
← 上一篇 表空间与独立表空间

做的事：同样1000行数据，一份按主键顺序插，一份打乱顺序插

代码SET GLOBAL innodb_monitor_enable='index_page_splits'; -- 顺序插入：id按0,1,2...999的顺序 INSERT INTO seq_pk (id, pad) SELECT ... ORDER BY id; -- 乱序插入：同样的id集合，打乱顺序 INSERT INTO rand_pk (id, pad) SELECT ... ORDER BY RAND();

验证：真实的页分裂次数，乱序比顺序多了近40%

实测 · 本机index_page_splits计数器真实增量 
顺序插入1000行后：  index_page_splits 真实增加了 14 次
乱序插入1000行后：  index_page_splits 真实又增加了 19 次（累计33）

顺序插入的14次分裂，本质上是B+树往末尾不断追加数据、页面写满后真实必须再开一个新页的正常增长——这种"尾部分裂"代价最小，几乎是必然发生的。乱序插入额外多出来的19次，真实是往已经存在、中间已经写满的页面里插入新记录，导致那些页面被迫真实"从中间劈开"成两个更空的页面——这种分裂比尾部追加更贵，而且分裂出来的两个新页通常都只有一半左右是满的。

验证：真实的磁盘空间差异，乱序表多花了约24%

实测 · 本机磁盘真实文件大小（同样1000行数据） 
seq_pk.ibd（顺序插入）：   344064 字节 (336KB)
rand_pk.ibd（乱序插入）：  425984 字节 (416KB)   ← 真实多花了约24%的空间
这24%的额外空间，直接对应着"从中间分裂"留下的那些只填了一半左右的页面——分裂之后的两个新页，为了给未来可能的插入留出空间，通常不会被填满，这真实是InnoDB为了避免"分裂完马上又得再分裂一次"做的权衡，但代价就是真实存储密度下降。这也是为什么业务里常见的建议是"主键尽量用自增ID或者单调递增的值，而不是UUID这类随机值"——不只是索引查找效率的问题，插入路径上真实产生的页分裂次数和磁盘空间浪费，也会因为主键的插入顺序不同而真实拉开差距。
