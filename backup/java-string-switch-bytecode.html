真实验证:hashCode相同的两个字符串，switch真实不会认错

"Aa"和"BB"是Java里经典的hashCode碰撞例子——先验证碰撞真实存在，再验证switch语句会不会因此把这两个值搞混。

StringSwitchBytecodeDemo.java switch (s) { case "Aa": return "特殊值Aa"; case "BB": return "特殊值BB"; ... }
真实实测 
"Aa".hashCode()=2112, "BB".hashCode()=2112, 真实是否相等: true
classify("Aa")=特殊值Aa, classify("BB")=特殊值BB (若switch只用hashCode不用equals,这两者会混淆; 真实结果证明没有混淆)

真实结果证明即使"Aa"和"BB"的hashCode()真实完全相同(都是2112)，switch依然正确地把它们分派到了各自对应的分支——如果底层真的只靠hashCode做判断，这两个case在字节码层面会变得无法区分。真实结果说明背后一定还有额外的校验步骤。

真实反编译:switch真实是lookupswitch(hashCode)+equals()两层结构

javap -c StringSwitchBytecodeDemo static java.lang.String classify(java.lang.String);
真实实测(javap -c 反编译结果) 
    aload_1
    invokevirtual  Method java/lang/String.hashCode:()I
    lookupswitch  { // 4
        -1396355227: 66
        -1361513063: 80
               2112: 94     <-- "Aa"和"BB"共享同一个hashCode,跳到同一个偏移量94
           93029210: 52
            default: 119
    }
94: aload_1
    ldc            String BB
    invokevirtual  Method java/lang/String.equals:(Ljava/lang/Object;)Z
    ifeq           108        <-- 不等于"BB",继续往下试
    iconst_4
    istore_2
    goto           119
108: aload_1
    ldc            String Aa
    invokevirtual  Method java/lang/String.equals:(Ljava/lang/Object;)Z
    ifeq           119
    iconst_3
    istore_2
字节码真实证明了这是一个"哈希分组+顺序equals"的两阶段设计。第一阶段，编译器真实先调用hashCode()，用lookupswitch指令根据哈希值跳转——"Aa"和"BB"因为哈希值相同，真实被分到了同一个跳转目标(偏移量94)。第二阶段才是关键:跳到94之后，字节码真实依次用equals()挨个比较该哈希值组内的所有候选字符串(先试"BB"，不等于就继续试"Aa")，只有equals()真实返回true的那个候选才会给istore_2赋对应的case序号，最后这个序号才会驱动真正的业务分支跳转。这个设计和HashMap处理哈希碰撞的思路本质相同——哈希值只是用来快速缩小候选范围的过滤器，真正决定"是不是同一个值"的，永远是equals()。
