逃逸分析:一个变量什么时候会从栈搬到堆

一个变量放在栈上还是堆上,不由 new 或者 &T{} 这样的写法决定,而是由编译器的逃逸分析决定。这篇先读 -m 的诊断,再用 AllocsPerRun 数出真实的分配次数,发现两者并不总是一致;然后量出栈上限、对照内联的影响,最后量一量逃逸到底多花多少。

128 KiB / 64 KiB
显式局部变量 / 隐式分配(make、new、&T{})能留在栈上的上限(二分法实测)
32 字节
变长 make 的栈上缓冲:n=4 个 int 零分配,n=5 个就分配 1 次
3.3 倍
同样调用 500 万次,逃到堆上的 33.3 ms,留在栈上的 10.1 ms

编译器的措辞有三种:moved to heap: p 说的是变量 p 本身被搬到堆上;… escapes to heap 说的是某个表达式的值(make 的结果、转成接口的值、函数字面量)要放在堆上;does not escape 是留在栈上。第 17 行的 p escapes to heap 说的是“把 p 转成接口这一步”,它并不等于运行时一定有一次分配,下一节会看到。

三个出乎意料的结果。第一,toInterface 传的是常量 Point{1,2},编译器直接指向只读数据,0 次分配;换成运行时才知道的值就是 1 次。我在编译器源码 walk/convert.go 里读到同一个函数的几个分支:零大小用 zerobase、单字节或布尔用 staticuint64s 表、只读全局直接用,最后才调用运行时分配。int 的 255 / 256 分界来自 runtime/iface.go 的 convT64:值小于 len(staticuint64s)(256)时直接取表项,否则调 mallocgc,实测与之一致。第二,变长 make([]int, n) 的诊断是 does not escape,但并不保证零分配:源码(walk/builtin.go 的 walkMakeSlice 与 base/flag.go 里的 VariableMakeThreshold = 32)写的是“如果 cap ≤ K,就用栈上的 [K]E,否则调 makeslice”,K 由 32 字节除以元素大小得到——int 是 8 字节,所以 K = 4,实测正是 n=4 零分配、n=5 一次分配。第三,-d=variablemakethreshold=1024 把阈值调大后 n=64 也是零分配,-N 关闭优化后变长 make 就回到一次分配,而常量长度的 make(10) 在 -N 下仍是零。

栈上能放多大

实测 · 本机执行输出 
  var a [N]byte(显式声明的局部数组):131072 字节仍在栈上,131073 字节被放到堆上(= 128 KiB + 0 字节为界)
  make([]byte, N)(常量长度):65536 字节仍在栈上,65537 字节被放到堆上(= 64 KiB + 0 字节为界)
  new([N]byte):65536 字节仍在栈上,65537 字节被放到堆上(= 64 KiB + 0 字节为界)
  &[N]byte{}(取地址的复合字面量):65536 字节仍在栈上,65537 字节被放到堆上(= 64 KiB + 0 字节为界)

数字和源码里的两个常量对得上:ir/cfg.go 里 MaxStackVarSize 是 128 KiB(显式的 var x T),MaxImplicitStackVarSize 是 64 KiB(new(T)、&T{}、make([]T, n))。二分法的结果是恰好以字节为界:131072 与 65536 在栈上,多一个字节就去了堆。注意这里是 arm64 上 Go 1.27.1 的数字,其它版本的上限可能不同。

-m -m 的 flow 链从右往左读:flow: ~r0 ← &p 是“返回值 ~r0 取得了 p 的地址”,所以 p 的生命周期要超过函数。接口参数那条链里出现了 {heap},意思是它流进了编译器无法证明不逃逸的调用(fmt.Fprintln 的 ...any 参数)。too large for stack 是大小原因,不涉及数据流。看到 moved to heap 时,往上找 flow 链里第一个“address-of”和最后一个流向,就能定位是哪一行造成的。

同一段代码内联与否结论相反

实测 · 本机执行输出 
  默认(newPoint 被内联进 sum):
    main.go:10:6: can inline newPoint    ← func newPoint() *Point { return &Point{1, 2} }
    main.go:13:31: inlining call to newPoint    ← func sum() int { p := newPoint(); return p.X + p.Y }
    main.go:10:33: &Point{...} escapes to heap    ← func newPoint() *Point { return &Point{1, 2} }
    main.go:13:31: &Point{...} does not escape    ← func sum() int { p := newPoint(); return p.X + p.Y }
    sum() 每次调用的分配次数:0
  -gcflags=-l(关闭内联):
    main.go:10:33: &Point{...} escapes to heap    ← func newPoint() *Point { return &Point{1, 2} }
    sum() 每次调用的分配次数:1

逃逸分析是在函数边界上做的。newPoint 返回指针,在它自己的诊断里永远逃逸;但被内联进 sum 之后,指针没有离开 sum,这个值就留在了栈上。所以排查分配问题时,-gcflags=-l 能帮你分辨“这次分配是不是只因为某个调用没被内联”。

逃逸的代价

实测 · 本机执行输出 
  byValue(栈)     500 万次:耗时中位 10.1 ms(最小 9.7 / 最大 12.9);Mallocs +2,TotalAlloc +80 字节,GC 次数 +0
  returnPtr(堆)   500 万次:耗时中位 33.3 ms(最小 33.0 / 最大 33.8);Mallocs +5000003,TotalAlloc +80000288 字节,GC 次数 +21

代价有两层:每次调用多一次 mallocgc(这里 16 字节),以及这些堆对象带来的 GC 工作。上面的 33.3 ms 里包含了这 21 次 GC 的成本,不能全算成分配本身。byValue 每次调用约 2 纳秒(10.1 ms / 500 万),这是 //go:noinline 函数调用本身的量级;不要把“3.3 倍”套到别的程序上,它只说明在这个最小例子里,逃逸把一次几乎没有成本的调用变成了一次分配加回收。
