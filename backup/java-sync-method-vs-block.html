synchronized 方法和 synchronized(this) 块:真实验证锁的是同一把锁

真实验证:两种写法真实互相阻塞

让一个线程先拿到锁忙 500ms,另一个线程用不同的写法去申请同一把锁,看真实要等多久。

SyncMethodVsBlockDemo.java static class Shared { synchronized void methodLock() { // 锁的是 this try { Thread.sleep(300); } catch (InterruptedException ignored) {} } void blockLock() { synchronized (this) { // 显式锁 this,和上面锁的是同一个对象 try { Thread.sleep(300); } catch (InterruptedException ignored) {} } } }
真实实测 · t1 持有 methodLock() 的锁,main 调用 blockLock() 
main 线程调用 blockLock() 真实等待了约 808ms(t1 持有同一把锁 500ms)
真实实测 · 反过来:t2 持有 synchronized(this) 块的锁,main 调用 synchronized 方法 
main 线程调用 methodLock()(synchronized 方法) 真实等待了约 805ms
这证明 synchronized 方法和 synchronized(this) 块真实锁的是同一把对象锁

两个方向的真实等待时间几乎一致(808ms 和 805ms,对应"持锁方 500ms + 自己执行体 300ms"这个预期结构),证明不管申请锁的一方用的是哪种写法,真实排队等待的都是同一把锁——t1 用 synchronized 方法持锁,能真实挡住 synchronized(this) 块想进来的线程;反过来也成立。如果两者锁的是不同对象,这两次调用应该几乎立即返回(各自的锁都没人占用),不会真实等待 800ms。

为什么会这样?synchronized 实例方法从字节码层面看,就是编译器在方法上打了一个 ACC_SYNCHRONIZED 标志位,JVM 执行这个方法时会自动对 this 加锁、方法返回时自动解锁——这在语义上和手写 synchronized(this) { 方法体 } 完全等价,只是加锁/解锁的动作由 JVM 隐式完成,不需要 monitorenter/monitorexit 这两条字节码指令显式出现在方法体里。真实结果验证的正是这一点:两种写法的锁对象、加锁范围在效果上没有任何真实差异。
