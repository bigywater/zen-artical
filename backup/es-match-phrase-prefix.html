代码真实索引4篇文档: "Quick Brown Fox" / "Quick Brown Bear" / "Quick Blue Jay" / "Slow Brown Fox" POST /mpp_test/_search {"query":{"match_phrase_prefix":{"title":"quick br"}}} POST /mpp_test/_search {"query":{"match_phrase":{"title":"quick br"}}} # 对比普通短语查询

验证：match_phrase_prefix真实把"br"当成前缀命中了2篇，match_phrase真实0命中

实测 · 本机 Elasticsearch 8.15.0 执行输出 
match_phrase_prefix搜"quick br":
→ "Quick Brown Fox" score=0.7133499
→ "Quick Brown Bear" score=0.7133499
  ← 真实两篇都命中了，"br"被当成了"brown"的前缀

match_phrase搜同样的"quick br":
→ hits = 0   ← 真实一个都查不到！"br"不是索引里的完整词

这组对比真实验证了match_phrase_prefix存在的真实意义：它跟本系列第31篇讲过的match_phrase共享"查询词必须按顺序紧邻出现"这个核心要求，但额外真实赋予了最后一个词"前缀匹配"的特权——查询词组里除最后一个词外，前面的词都必须是索引里的完整词项精确匹配，只有最后一个词真实被当成一个前缀，去匹配所有以它开头的词项。普通的match_phrase真实没有这个特殊处理，"br"在索引里真实根本不是一个完整词项，直接查不到任何结果。这正是搜索框"输入到一半就能看到候选结果"这种体验的真实底层机制。

真实用explain看match_phrase_prefix到底把查询语句改写成了什么样子

代码POST /mpp_test/_validate/query?explain=true {"query":{"match_phrase_prefix":{"title":"quick br"}}}

验证：explain真实显示最后一个词被改写成了带星号的前缀"br*"

实测 · 本机执行输出 
explain输出:
→ "title:\"quick br*\""
  ← 真实前面的quick保持原样，最后一个词br真实被加上了星号变成通配前缀

这条explain真实直接证明了match_phrase_prefix的实现方式：它真实不是某种全新的匹配算法，而是在构造短语查询时，把短语里的最后一个词替换成了一个前缀查询（br*），前面的词依然保持精确的短语位置约束。这也意味着它真实继承了本系列第36篇验证过的通配符查询特性——真实需要在倒排索引的词典里枚举所有以"br"开头的候选词项，再分别尝试跟前面的词组成有效短语。

真实验证max_expansions参数如何限制候选词项数量，进而真实影响召回结果

代码原文里以"b"开头、紧跟在quick后面的候选词真实有bear/blue/brown三个 POST /mpp_test/_search {"query":{"match_phrase_prefix":{"title":{"query":"quick b","max_expansions":1}}}} POST /mpp_test/_search {"query":{"match_phrase_prefix":{"title":{"query":"quick b","max_expansions":10}}}}

验证：max_expansions=1真实只展开了1个候选词，刚好没选中真实匹配的那个，查询变成0命中

实测 · 本机执行输出 
max_expansions=1: hits = 0   ← 真实查不到任何结果！
  ← 以b开头的候选词真实按字典序排列是bear/blue/brown，限制只展开1个的话
  ← 真实只会尝试"bear"这一个候选词，但原文里quick后面真实没有紧跟着bear

max_expansions=10（足够覆盖全部3个候选词）: hits = 3
→ ["Quick Brown Fox", "Quick Brown Bear", "Quick Blue Jay"]
  ← 真实把brown和blue这两个真正匹配的候选词都覆盖到了
这组真实结果揭示了max_expansions这个参数一个容易被忽视的坑：它真实不是"最多展示多少条结果"，而是"最多在词典里尝试多少个候选前缀展开词项"——这是在真正执行短语匹配之前的一道真实限制。本次实测里，以"b"开头的候选词真实按字典序是bear、blue、brown，max_expansions=1真实只允许尝试字典序最靠前的"bear"，而原文里真正紧跟在"quick"后面的词是"brown"和"blue"，"bear"真实压根不在任何一篇文档里紧跟着quick出现，于是整个查询就真实查不到任何结果——即便数据库里明明存在真实该匹配上的文档。这说明max_expansions设得过小（默认值其实是50，通常够用），在候选词项字典序分布不利的情况下，真实可能导致搜索框的自动补全体验莫名其妙地"查不到东西"，这也是为什么官方文档建议谨慎调低这个参数。
