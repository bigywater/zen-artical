启动与内存

实测 · 本机执行输出 
  Tomcat:端口可连接 中位 805 ms(范围 767~859);第 1 次请求 35.9 ms,第 2 次 1.4 ms;常驻内存 启动后 163 MB,请求 2 次后 169 MB
  Jetty:端口可连接 中位 860 ms(范围 840~900);第 1 次请求 47.0 ms,第 2 次 1.4 ms;常驻内存 启动后 170 MB,请求 2 次后 174 MB

两者相差几十毫秒、几个 MB,范围略有重叠。

    本文用到的工具与边界

    • 本机 macOS 27 arm64 / OpenJDK 21.0.12(Homebrew) / Spring Boot 4.0.8(Spring Framework 7.0.9、Tomcat 11.0.24) / Spring Cloud 2025.1.3;用 javac 编译、java 直接运行,依赖由 Maven 从 Maven Central 解析;数字每次运行会有小幅抖动。同一份应用代码(spring-boot-starter-webmvc,一个 RestController),只换 classpath;Jetty 方案是把 spring-boot-starter-jetty 的依赖解析出来,再从 classpath 里去掉 tomcat-embed、spring-boot-tomcat、spring-boot-starter-tomcat 的 jar;压测端是 JDK HttpClient + 虚拟线程,与被测应用在同一台机器上,每个组合 2 轮,所以绝对数值只能在表内比较;Maven Central 的查询是用 maven-metadata.xml 和直接请求 4.0.8 的 pom
    • 没有验证:HTTP/2、TLS、压缩、WebSocket 在两个容器上的差别;长时间运行的内存与 GC;更大的并发度和更大的响应体;请求头 400 与 431 的差别背后各自是什么配置项(只观察到结果);Jetty 虚拟线程为什么在默认线程池上限下被卡住(只观察到加大 threads.max 之后恢复,没有读源码);Undertow 在其他 Boot 版本里的表现;Tomcat 的 keep-alive 超时与 Jetty 的 idle timeout 是不是同一种含义(这里只测了「发一个请求后空闲多久被服务端关闭」)
