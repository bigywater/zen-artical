直方图:桶的选取、分位数误差与 histogram_quantile 的近似

Prometheus 的 histogram_quantile 有多准?桶该怎么划分?数据超出最大桶时会怎样?rate 的窗口怎么影响分位数?桶越多序列数增长多快?这篇用 Prometheus 3.15.0 和同一批 10 万个样本逐项量出来。

  桶越宽,线性插值的误差越大;最大误差出现在分位数落进宽桶的时候。桶边界要覆盖要关心的分位数和阈值附近(例如 SLO 的 500 ms),并不是桶越多越好

误差最大出现在分位数落进宽桶时;桶的位置比数量重要。

边界与 +Inf

实测 · 本机执行输出 
  数据                 | p50 估计(ms) | p99 估计(ms) | 用 sum / count 算的平均值(ms)
  -------------------+------------+------------+------------------------
  (a)全部 3000~9000 ms | 1000.0     | 1000.0     | 5996.7                 
  (b)全部恰好 100 ms     | 75.0       | 99.5       | 100.0                  
  (c)全部 100.001 ms   | 175.0      | 248.5      | 100.0                  
  超出最大有限桶的数据都进了 +Inf 桶,histogram_quantile 在落进 +Inf 桶时只能返回最大有限桶的上界(这里 1000),平均值(sum / count)才反映真实水平;桶边界是“小于等于”,恰好 100 ms 的请求进 le=100 的桶,估计值是这个桶 (50, 100] 内线性插值的位置(p50 = 75、p99 = 99.5),不是 100 本身;100.001 ms 的请求落进下一个桶 (100, 250]

超出最大有限桶的数据只能返回最大有限桶的上界;恰好落在边界上的值归入“小于等于”的桶。

    本文用到的工具与边界

    • 本机 macOS 27 arm64 / Python 3.14.8 / Go / nginx / Envoy / etcd / Consul / Nacos / OpenTelemetry / Prometheus(按各篇注明用到哪些及版本);所有服务都是本机自己起的进程,端口 9150 以上,只监听 127.0.0.1,不连任何外部服务,不碰本机已有的实例;故障用 kill -9 进程、让连接断开或在代码里注入延迟与错误来制造;计时用 time.perf_counter,数字每次运行会有小幅抖动。Prometheus 3.15.0(经典直方图,没有开启 native histogram),prometheus_client 0.26.0;样本是固定种子生成的 10 万个,桶的“相对误差”按真实分位数计算;rate 窗口那节每个时刻、窗口各查一次;每节只跑了一次,histogram_quantile 的结果每次运行基本一致(桶内线性插值是确定的)
    • 没有验证:native histogram(Prometheus 3.x 的新直方图,桶自动按指数划分,序列数固定);Summary 类型的分位数误差;OpenTelemetry 的 explicit bucket / exponential histogram;多个实例的 histogram 在桶划分不一致时怎么聚合;Grafana / VictoriaMetrics 对 histogram_quantile 的实现差异
