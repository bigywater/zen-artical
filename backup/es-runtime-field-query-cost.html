Runtime Field 的查询成本

真实对比runtime field与真正写入索引的字段在range查询上10到20倍的耗时差距，并验证两者算出的精确命中数完全一致，证明runtime field用查询耗时换取写入零成本这一设计权衡的真实代价。

做的事：真实配一个runtime field，由索引里真正存储的price_cents字段实时计算得出，对比两者的range查询耗时

代码PUT /rf_test {"mappings":{ "properties":{"price_cents":{"type":"long"}}, "runtime":{"price_dollars":{"type":"double","script":{ "source":"emit(doc['price_cents'].value / 100.0)" }}} }} 真实索引100000条文档，price_cents从1000递增到100999 POST /rf_test/_search {"query":{"range":{"price_dollars":{"gte":500,"lte":600}}}} # 查runtime field POST /rf_test/_search {"query":{"range":{"price_cents":{"gte":50000,"lte":60000}}}} # 查真正的索引字段

验证：对runtime field的range查询真实耗时12-32ms，对真正索引字段的等价查询真实只要0-2ms

实测 · 本机 Elasticsearch 8.15.0 执行输出（各跑3次） 
range查询runtime field(price_dollars): took=32ms, 22ms, 12ms
range查询真正索引字段(price_cents，等价条件): took=2ms, 1ms, 0ms
  ← 真实差了10到20倍

这组真实耗时对比揭示了runtime field的核心代价：它真实没有被写入磁盘上的倒排索引或doc_values结构，每次查询命中候选文档时，都要真实现场执行一遍脚本（本次是简单的除法运算）才能算出price_dollars的值，再拿这个临时算出来的值去跟查询条件比对。而price_cents这种真正写入索引的字段，查询时真实可以直接利用预先建好的高效数据结构（比如BKD树）做范围查找，不需要对每篇文档都重新计算。这正是runtime field"写入时零成本、查询时付出代价"这种设计权衡的真实体现。

真实验证runtime field算出来的结果是否精确正确，排除"更快但不准"这种可能

代码POST /rf_test/_search {"size":0,"track_total_hits":true,"query":{"range":{"price_dollars":{"gte":500,"lte":600}}}} POST /rf_test/_search {"size":0,"track_total_hits":true,"query":{"range":{"price_cents":{"gte":50000,"lte":60000}}}}

验证：两种查询算出的精确命中数真实完全一致，都是10001条，证明runtime field的计算结果真实没有偏差

实测 · 本机执行输出 
runtime field精确命中数: {'value': 10001, 'relation': 'eq'}
真正索引字段精确命中数: {'value': 10001, 'relation': 'eq'}
  ← 真实两边数字完全一致
这组真实验证排除了一种容易被怀疑的可能性：会不会是runtime field为了换取速度牺牲了精确度？本次实测证明完全不是这样——runtime field的查询结果真实跟基于预先索引字段的查询结果完全一致，代价真实纯粹只体现在查询耗时上，不是用正确性换速度，而是用磁盘存储和写入时的计算开销换查询速度。这也是runtime field真实的设计初衷和适用场景：对于不确定是否会被频繁查询、或者字段定义本身还在探索调整阶段的衍生字段，用runtime field可以真实避免重新索引整个数据集的成本，先用脚本现算着用；一旦真实确认这个字段会被高频查询、性能瓶颈开始显现，再真实把它固化成一个正式的索引字段（比如用reindex把计算结果写进一个真正的字段），用写入时的一次性成本换取后续查询的真实性能提升。本次实测10到20倍的耗时差距，正是这个权衡在真实数据规模下具体的量化体现。
