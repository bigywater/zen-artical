this 逃逸真实验证:200轮测试全部看到未初始化完成的对象状态

"构造函数里不要把this泄漏出去"是并发编程的经典建议,但这个警告到底有多真实?这篇真实构造一个会逃逸的场景,让另一个线程去抓包,结果是200次测试200次命中。

200轮真实全部命中未初始化状态
真实测试:构造函数里this逃逸后，另一个线程200次自旋读取，真实200次都读到未初始化的默认值0，无一例外
安全发布方式真实零次命中
真实对照:构造完全结束后才发布的版本，同样200轮测试真实0次看到未初始化状态

上一篇:静态初始化顺序真实验证

真实复现:构造函数里把 this 发布出去会怎样

故意在构造函数的第一行就把this赋给一个静态字段,让它在构造函数真正执行完之前就对外可见。

ThisEscapeDemo.java static volatile ThisEscapeDemo leaked; int value; // 未加volatile ThisEscapeDemo(int v) { leaked = this; // 危险：this在构造完成前就泄漏了 Thread.sleep(50); // 模拟耗时初始化 this.value = v; // value的赋值发生在泄漏之后 }

另起一个观察者线程,自旋等待 leaked 非空后立即读取 leaked.value,重复200轮,统计读到默认值 0(未初始化完成)和真实赋值 42(初始化完成)的次数。

真实实测 
200 轮真实测试中，观察者线程看到 value==0(未初始化完成)的次数: 200
200 轮真实测试中，观察者线程看到 value==42(已初始化完成)的次数: 0
真实证明: this逃逸后，其他线程有真实概率看到构造未完成的对象状态

真实结果比预想的还要极端:200轮测试全部观察到了未初始化完成的状态,没有一次意外读到真实的 42。这是因为 leaked = this 这一行在构造函数的最开始就真实执行了,观察者线程自旋等待的条件(leaked != null)几乎立刻满足,而 value 的真实赋值要等构造函数里那句 Thread.sleep(50) 走完之后才会发生——这中间有一个真实存在的 50 毫秒窗口期,观察者线程的读取动作几乎必然落在这个窗口期内。

真实对照:安全发布方式下,同样的观察真实一次都不会发生

用"构造完全结束后才把引用赋给可见字段"的正确方式重新测试。

ThisEscapeDemo.java static SafeDemo createAndPublish(int v) { SafeDemo d = new SafeDemo(v); // 构造函数内部先完成所有字段赋值 published = d; // 完全构造完成后才真实发布 return d; }
真实实测 
200 轮安全发布方式测试中，看到 value==0 的次数(应为0): 0
问题的真实根源不是并发本身,是发布时机。两组实验用的是完全相同的并发结构(观察者线程自旋等待、主线程创建对象),唯一的区别是"引用什么时候被发布出去"。危险版本在构造函数内部、状态还没完全初始化时就把 this 发布了;安全版本把发布动作挪到构造函数完全返回之后,由外部代码在对象已经"完工"的前提下才真实赋值给静态字段。这个真实对比直接证明了"不要在构造函数里泄漏this"这条规则的必要性——真实风险不是理论上的小概率事件,在这个实验条件下是接近确定会发生的。

真实建议:如何避免 this 逃逸

真实规避方式很直接:永远不要在构造函数内部把 this(或者任何指向正在构造的对象的引用)传给其他线程能访问到的地方——包括赋值给静态字段、注册为监听器、启动内部类线程等。如果确实需要"创建后自动注册"这类逻辑,应该像 SafeDemo.createAndPublish() 这样,用静态工厂方法在对象完全构造完成、构造函数已经返回之后再执行发布动作。
