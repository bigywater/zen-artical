HashMap并发扩容真实验证:8线程并发put，真实丢了将近1/3的数据

JDK7的HashMap并发扩容会死循环，JDK8之后修复了死循环——但这不代表并发用普通HashMap就安全了。这篇真实用8个线程并发put 4万条不重叠的key，验证JDK17上到底会发生什么。

8个线程各自负责一段不重叠的key区间(避免"同一个key被多次put覆盖"这种干扰)，并发写入同一个普通HashMap。

真实结果证明并发问题真实存在，而且每轮丢失的数量都不一样(最严重一轮丢了超过30%),这符合并发bug"不确定性"的典型特征——具体丢多少取决于线程调度的真实时机。单线程对照组则真实精确等于期望值40000，排除了测试代码本身的逻辑错误。

真实丢数据的根本原因:resize()不是原子操作

没有异常比抛异常更危险。真实结果里最值得警惕的一点是"真实捕获到的异常次数=0"——如果并发写HashMap真实会抛异常(比如ConcurrentModificationException),问题反而更容易在开发阶段暴露。但真实情况是:当多个线程同时触发resize()(扩容并重新计算每个entry在新数组里的位置)，或者同时在同一个桶(bucket)的链表/红黑树上做插入，JDK17的实现真实会因为"检查数组容量→创建新节点→挂到链表尾部→更新size"这几步不是原子的，导致某些线程的写入真实被另一个线程的并发写入覆盖或丢弃，但两个线程各自的方法调用本身都"正常返回"，不会抛任何异常。程序在功能测试、单线程压测下真实完全正常，只有在真实的高并发生产流量下才会暴露出数据对不上的诡异问题。

正确的做法是用ConcurrentHashMap替代普通HashMap，或者用Collections.synchronizedMap()包装后手动同步——这两种方式都能保证并发写入的真实原子性和可见性，避免这种静默丢数据的问题。
