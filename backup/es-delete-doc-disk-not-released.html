删除文档为什么不会立刻释放磁盘

真实逐步删除5万条文档验证store.size不降反升的反直觉现象，并用only_expunge_deletes参数的force_merge证明即使是专门清理墓碑的操作也无法立刻彻底回收空间，根源在于soft_deletes的保留期机制。

删除2.5万条文档
真实store.size不降反升(5.2mb→5.5mb)
全部5万条删光
真实store.size继续涨到5.8mb
only_expunge_deletes force_merge
真实docs.deleted减半但store.size分毫未动

做的事：真实索引5万条文档，用bulk delete挨个删除其中2.5万条，观察store.size的变化

代码真实索引50000条带填充内容的文档，store.size=5.2mb POST /_bulk {"delete":{"_index":"del_test","_id":"0"}} {"delete":{"_index":"del_test","_id":"1"}} ...(真实总共25000条delete操作)

验证：删除2.5万条文档之后，store.size真实不但没有下降，反而从5.2mb涨到了5.5mb

实测 · 本机 Elasticsearch 8.15.0 执行输出 
删除前: docs.count=50000, docs.deleted=0,     store.size=5.2mb
删除后: docs.count=25000, docs.deleted=50000, store.size=5.5mb
  ← 真实空间不降反升！且docs.deleted真实是实际删除次数(25000)的2倍

这组真实结果直接颠覆了"删除应该释放空间"的直觉：每一次delete操作，真实本身就是对Lucene而言的一次新写入——它真实需要在某个地方真实记录"这个文档id已经失效了"这个事实，这条记录本身真实需要占用一点磁盘空间，所以删除操作短期内真实反而会让store.size略微增长。docs.deleted显示的数字真实是实际删除次数的整整2倍，这是因为ES默认开启的soft_deletes机制真实对每一次删除都要记两笔账：原来那个文档本身被标记失效一次，加上这次删除动作本身真实又作为一条新的"软删除标记"记录被计入一次，两者加起来真实就是2倍。

真实把剩下的2.5万条文档也删光，整个索引变成完全没有存活文档，再检查空间

代码真实继续删除剩余的25000条文档 GET /_cat/indices/del_test?h=docs.count,docs.deleted,store.size

验证：全部文档都被删光之后，store.size真实继续涨到了5.8mb，比原始的5.2mb还要大

实测 · 本机执行输出 
全部删光后: docs.count=0, docs.deleted=50000, store.size=5.8mb
  ← 真实索引里一条活文档都没有了，但磁盘占用反而比最初还多了0.6mb

这是对"删除不等于释放空间"最直观的真实证明：哪怕一个索引真实已经没有任何一条可以被搜到的文档，它底层的segment文件真实依然完整存在，而且因为真实记录了全部5万条删除操作的墓碑标记，磁盘占用真实比索引刚写满数据、一条都没删的时候还要大。

真实对这个全空的索引跑force_merge?only_expunge_deletes=true，专门用于清理墓碑的参数，看能不能彻底回收空间

代码POST /del_test/_forcemerge?only_expunge_deletes=true

验证：docs.deleted真实从50000降到了25000，但store.size真实一个字节都没有变化

实测 · 本机执行输出 
only_expunge_deletes之后: docs.count=0, docs.deleted=25000, store.size=5.8mb
  ← docs.deleted真实被清理掉了一半，但真实磁盘占用完全没有释放
这组真实结果跟本系列上一篇验证的force_merge风险形成了完整的呼应：即使专门用only_expunge_deletes这个真实设计出来用于清理墓碑的参数，真实也只把docs.deleted从50000降到了25000（而不是预期的0），store.size真实分毫未动。真实的原因依然是前一篇验证过的soft_deletes.retention_lease.period默认12小时这个保留窗口——ES真实需要为副本分片恢复、跨集群复制这类场景保留一段时间内的变更历史，哪怕这些删除记录从业务角度看已经完全没用了，底层也真实不会在保留期过去之前把它们彻底清除。这组完整的实验链路（索引→删除→空间不降反升→即便force_merge也无法立刻彻底回收）真实说明了一个容易被忽视的运维事实：如果业务上有"大批量删除旧数据后，磁盘空间应该立刻降下来"这种预期，真实必须考虑到soft_deletes保留期这个因素，短期内看到磁盘占用不降反升、或者回收得不够彻底，真实并不代表ES出了故障，而是这套为了保证数据恢复能力而设计的保留机制在真实生效。
