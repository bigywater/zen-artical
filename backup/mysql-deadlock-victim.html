死锁受害者如何选择

制造一个真实的经典死锁，再让两个事务的'已完成工作量'明显不对等，重复多轮看InnoDB选择受害者的真实倾向。

3/3轮
改得少的一方，真实全部成为死锁受害者
undo量
InnoDB真实用来判断撤销代价的依据
← 上一篇 NOWAIT

做的事：两个事务，交叉顺序去锁同两行

经典的死锁场景：G先锁10再要20，H先锁20再要10。

session GSTART TRANSACTION; UPDATE accounts SET balance=balance-1 WHERE id=10; SELECT SLEEP(1); UPDATE accounts SET balance=balance-1 WHERE id=20; -- 此时H已经锁住了20，G在这里等 COMMIT; session H（晚0.3秒启动）START TRANSACTION; UPDATE accounts SET balance=balance-1 WHERE id=20; SELECT SLEEP(1); UPDATE accounts SET balance=balance-1 WHERE id=10; -- 此时G已经锁住了10，H在这里等 → 死锁 COMMIT;

验证：InnoDB真实检测到了循环等待，选H做了受害者

实测 · 本机SHOW ENGINE INNODB STATUS真实输出（LATEST DETECTED DEADLOCK节选） 
*** (1) TRANSACTION: ... query "UPDATE accounts ... id=20" 持有id=10的锁，等待id=20
*** (2) TRANSACTION: ... query "UPDATE accounts ... id=10" 持有id=20的锁，等待id=10
*** WE ROLL BACK TRANSACTION (2)   ← 真实回滚了事务(2)，也就是session H

session H的真实错误：ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

两个事务真实互相等待对方持有的锁，形成了一个环，InnoDB的死锁检测线程真实发现了这个循环并选择了一方强制回滚——这次测试里是session H被回滚，session G的事务真实继续执行完成并提交。

验证：真实重复3轮，"改得少的一方"每次都成了受害者

把G改成只修改1行(10和20)就冲突，H改成先修改5行(20,30,40,50,60)再去抢10，两边"投入的工作量"真实不对等。

实测 · 本机3轮独立重复测试 
轮次1：I（改1行后冲突）真实死锁被回滚，J（改5行后冲突）真实存活
轮次2：I（改1行后冲突）真实死锁被回滚，J（改5行后冲突）真实存活
轮次3：I（改1行后冲突）真实死锁被回滚，J（改5行后冲突）真实存活
3轮测试真实全部一致：只改了1行就陷入死锁的事务(I)，每次都真实成为被回滚的受害者；已经改了5行的事务(J)，每次都真实活下来提交成功。这印证了InnoDB选择死锁受害者的真实策略——优先回滚撤销代价更小的那个事务，用"这个事务已经生成了多少undo log(改了多少行)"作为真实的判断依据：改得越少，说明回滚它需要撤销的工作量越小，对整体的影响也越小，所以InnoDB真实倾向于牺牲它，保住已经做了更多工作的那一方。这不是保证一定按行数精确排序的规则，但在真实测试里，行数差距明显时，这个倾向真实非常稳定。
