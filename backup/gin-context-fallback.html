ContextWithFallback 与 c.Done()

很多人把 c 直接传给数据库或下游客户端当 context 用,以为请求取消时它们会跟着取消。默认并不会。这篇验证 ContextWithFallback 关闭和打开时 Done、Err、Deadline、Value 的行为,以及它对客户端断开时子 context 的影响。

400 ms
默认配置下 work(c) 没有被请求超时取消,自己跑满的时间
1502 ms vs 202 ms
客户端 200 ms 断开后,以 c 为父的子 context 结束的时间(关闭 / 打开 fallback)
T-1
只有打开 fallback 后 c.Value 才能读到 Request.Context 里的 trace 值

*gin.Context 实现了 context.Context 接口,所以能直接传给接受 context 的函数,但默认的 Done() 是 nil、Err() 是 nil、没有 deadline。也就是说,它对下游来说是一个永远不会取消的 context;c.Value 只能读到 c.Keys 里的值,读不到 Request.Context() 里的。

打开之后

实测 · 本机执行输出 
    ContextWithFallback=false:
      c.Done()==nil:true  c.Err()=<nil>  c.Deadline() ok=false
      c.Value("user")=alice  c.Value(ctxKey("trace"))=<nil>  c.Request.Context().Value(ctxKey("trace"))=T-1
      work(c):没有被取消,自己跑完 (400 ms)
      work(c.Request.Context()):context deadline exceeded 取消(101 ms)
    ContextWithFallback=true:
      c.Done()==nil:false  c.Err()=<nil>  c.Deadline() ok=true
      c.Value("user")=alice  c.Value(ctxKey("trace"))=T-1  c.Request.Context().Value(ctxKey("trace"))=T-1
      work(c):context deadline exceeded 取消(102 ms)
      work(c.Request.Context()):context deadline exceeded 取消(101 ms)

engine.ContextWithFallback = true 后,四个方法都转发给 c.Request.Context():中间件加的超时会让 work(c) 在 100 ms 左右被取消,trace 值也能读到。不想打开这个开关时,每次传 c.Request.Context() 也能得到同样的效果,代价是每个调用点都得记得这样写。

子 context 与客户端断开

实测 · 本机执行输出 
    ContextWithFallback=false 客户端 200ms 时断开 → 子 context 结束:context deadline exceeded,1502 ms 后
    ContextWithFallback=true  客户端 200ms 时断开 → 子 context 结束:context canceled,202 ms 后

以 c 为父创建子 context,打开 fallback 时,客户端断开会通过 Request.Context() 的取消传下来(202 ms);关闭时子 context 对断开一无所知,只能等自己的超时(1502 ms)。如果 handler 里有耗时的下游调用,这就是“客户端早走了,服务端还在白干”的来源之一。
