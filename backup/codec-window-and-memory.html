窗口与内存:往回看得越远压缩得越小,代价是什么

往回看得越远,压缩得越小,代价是内存。这篇量窗口多大才找得到重复、窗口开大了为什么还可能找不到、解压端为什么会报“需要太多内存”,以及每个对象单独压缩要付出多少压缩比。

重复内容相隔 1 MiB 时,zstd 级别 3 开始能匹配的最小窗口(2 MiB);windowLog 20 找不到
Frame requires too much memory
压缩端用了 windowLog 28,命令行 zstd -d 默认解压失败的错误;加 --long=28 才行

匹配只能指向窗口内的内容。重复的内容相隔 1 MiB,windowLog 20(1 MiB)找不到,windowLog 21(2 MiB)才行;相隔 5 MiB 要 windowLog 24。对 gzip 来说窗口固定是 32 KiB,更远的重复统统错过。

窗口大也不一定找得到

实测 · 本机执行输出 
  级别 3,windowLog 27,不开 LDM                → 17202831 字节(425615 字节减去填充),22 ms
  级别 3,windowLog 27 + enable_ldm          → 16993311 字节(216095 字节减去填充),37 ms
  级别 3,windowLog 20(1 MiB)+ enable_ldm    → 17203150 字节(425934 字节减去填充),36 ms

相隔 16 MiB 的重复,级别 3 开了 windowLog 27 仍然没找到,因为搜索用的哈希表容量有限,老位置被覆盖。长距离匹配(enable_ldm)另建结构专门找远处的重复,开了才找到;但 LDM 仍受窗口限制。

压缩端声明的窗口决定了解压端需要的内存。windowLog 27 的帧在解压端限制 64 MiB 时失败,windowLog 28 的帧命令行默认就解不了,要 --long=28。给别人分发压缩文件时,窗口不要开得比对方的内存大。

同样 32 KiB 窗口,zstd-19 比 zlib-9 只小 4%;放开窗口,zstd-3 在 1 MiB 窗口下就比 zlib-9 小 9%。zstd 比 gzip 小,窗口是原因之一。

窗口越大,压缩和解压需要的内存越多(流式解压 0.2 MiB 到 20.4 MiB),但窗口超过数据中重复的间隔后,压缩后的大小就不再改善(windowLog 18 之后基本不变)。

不要每个对象单独压缩

实测 · 本机执行输出 
        每块大小     块数       压缩后总字节     压缩比      比一整块大
         4KiB   2048      2705807   3.10×      62.0%
        16KiB    512      2376431   3.53×      42.3%
        64KiB    128      2007345   4.18×      20.2%
       256KiB     32      1759232   4.77×       5.3%
      1024KiB      8      1679330   5.00×       0.5%
      8192KiB      1      1670198   5.02×       0.0%

每个对象单独压缩等于每次重置窗口。4 KiB 的块压缩比 3.10×,整块是 5.02×;块到 256 KiB 才接近(4.77×)。小对象要攒批或用字典(下一篇)。
