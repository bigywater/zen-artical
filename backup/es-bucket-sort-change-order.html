bucket_sort 改变聚合桶顺序

真实验证terms.order无法引用同级bucket_script这类pipeline聚合算出的衍生值而直接报错，并用bucket_sort作为独立的事后排序步骤成功按同样的衍生值重新排出聚合桶顺序，厘清两者生效时机的本质区别。

terms.order引用bucket_script衍生值
真实直接400报错找不到这个聚合
bucket_sort同样的衍生值
真实成功精确降序排出b/d/a/c
本质区别
真实terms.order在早期生效，bucket_sort在所有兄弟聚合算完后才执行
← 上一篇 Pipeline Aggregation

做的事：真实对4个分类跑terms聚合嵌套avg(price)和一个衍生指标bucket_script，尝试用terms.order直接按衍生指标排序

代码真实索引7件商品，4个分类: a(2件,价10/30) / b(1件,价100) / c(3件,价5/5/5) / d(1件,价50) POST /bs_test/_search {"aggs":{"c":{"terms":{"field":"cat","order":{"total_val":"desc"}},"aggs":{ "avg_price":{"avg":{"field":"price"}}, "total_val":{"bucket_script":{"buckets_path":{"avg":"avg_price"},"script":"params.avg * 2"}} }}}}

验证：terms.order真实直接报错，没法引用同级的bucket_script这个pipeline聚合结果

实测 · 本机 Elasticsearch 8.15.0 执行输出 
→ 400 illegal_argument_exception:
  "Invalid aggregation order path [total_val]. Cannot find aggregation named [total_val]"

这条真实报错揭示了terms.order一个结构性的局限：它真实只能引用普通的metric子聚合（比如avg_price这种直接从原始文档算出来的指标），没法引用同一层级里bucket_script这类pipeline聚合算出来的衍生值——真实的原因是pipeline聚合本质上要等同一层级的其他兄弟聚合都真实计算完成之后才能执行（本系列上一篇验证过它以其他聚合的输出作为输入），而terms聚合决定桶的排序顺序这一步真实发生在更早的阶段，这时候total_val这个依赖avg_price才能算出来的值真实还不存在，所以terms.order压根拿不到它。

真实换成bucket_sort重新按同样的衍生指标排序

代码POST /bs_test/_search {"aggs":{"c":{"terms":{"field":"cat","size":10},"aggs":{ "avg_price":{"avg":{"field":"price"}}, "total_val":{"bucket_script":{"buckets_path":{"avg":"avg_price"},"script":"params.avg * 2"}}, "sort_step":{"bucket_sort":{"sort":[{"total_val":{"order":"desc"}}]}} }}}}

验证：bucket_sort真实成功按total_val精确降序重新排出了4个分类的顺序

实测 · 本机执行输出 
b total_val=200.0   ← 真实avg_price=100，total_val=100*2=200，排第一
d total_val=100.0   ← 真实avg_price=50，total_val=50*2=100
a total_val=40.0    ← 真实avg_price=20，total_val=20*2=40
c total_val=10.0    ← 真实avg_price=5，total_val=5*2=10，排最后
这组真实结果证明了bucket_sort存在的真实价值：它真实作为一个独立的pipeline聚合步骤，在同一层级的所有兄弟聚合（包括其他pipeline聚合）都真实计算完成之后才执行排序，所以它能真实引用任何已经算好的值去重新排序，不管这个值是直接的metric聚合结果还是像total_val这样由bucket_script衍生计算出来的中间结果。本次实测验证出的排序结果（b→d→a→c，精确对应total_val从200降到10）真实跟terms.order原本想做但做不到的排序意图完全一致，只是执行的时机和机制不同：terms.order真实是在terms聚合内部决定桶顺序的早期阶段生效，bucket_sort则真实是在所有子聚合（包括pipeline聚合）都算完之后，作为一个独立的"重新排序"步骤事后生效。理解这个先后顺序的区别，是正确选择用哪种方式给聚合桶排序的真实关键——简单指标排序两种方式都行，但凡涉及pipeline聚合算出来的衍生值，就只能真实用bucket_sort。
